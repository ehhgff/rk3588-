

这是一个为 **RK3588 开发板**量身打造的系统性能监控脚本。很多初学者看到一大段 Shell 代码会感到无从下手，下面我们把脚本“翻译”成人话，一步步拆解它的结构、功能，以及你如何在自己的 RK3588 上跑起来。

---

### 一、这个大脚本是干什么的？

简单说，**它让你在电脑上远程运行 RK3588 上的 `rktop` 监控工具，并在运行前后自动采集 CPU、内存、温度、NPU、GPU 等关键信息，最后生成一份性能对比报告**。

`rktop` 是一个类似 `htop` 的终端 UI 工具，专为 Rockchip 设计，能同时显示 CPU/GPU/NPU 等多项负载。脚本将枯燥的单次监控，变成了一套自动化的“体检流程”。

---

### 二、脚本的“骨架”：按执行顺序看懂它

脚本从上到下执行，我们把它分成几个“房间”，每进入一个房间就做一件事。

#### **房间 0：安全设置与欢迎横幅**
```bash
set -euo pipefail
```
这是脚本的“安全帽”。`-e` 表示任何命令出错就立刻停止，`-u` 禁止使用未定义的变量，`-o pipefail` 确保管道中任意一环失败都视为整体失败。这能避免错上加错。

接下来 `LOG_FILE` 定义日志文件位置，日志同时打印到屏幕和文件，方便事后查看。

#### **房间 1：配置区 —— 你可以修改的地方**
```bash
BOARD_IP="${1:-${BOARD_IP:-192.168.138.136}}"
SSH_USER="${SSH_USER:-root}"
TIMEOUT_SEC="${TIMEOUT_SEC:-60}"
```
这里定义了所有可调参数。`${1:-...}` 表示优先使用命令行第一个参数，没有就用默认 IP。所以你可以这样运行：
```bash
./test_rktop_on_board.sh 192.168.1.100   # 指定 IP
BOARD_IP=192.168.1.100 ./test_rktop_on_board.sh   # 环境变量指定
```
对于初学者，**修改默认 IP 和 SSH 用户是你最常做的事**。

#### **房间 2：日志函数 —— 统一输出格式**
```bash
log_ok()    { log "OK   " "$1"; }
log_err()   { log "ERROR" "$1"; }
```
这些函数让脚本输出带时间戳、日志级别的信息，看起来整齐。你不必深究，只要知道它们负责“说话”就行。

#### **房间 3：连接方式检测 —— 自动选 SSH 或 ADB**
`detect_remote` 函数会先尝试 SSH 连接，失败再试 ADB。这种“自动挡”设计很适合初学者：**无需指定连接方式，脚本自己猜**。如果你确定要用 ADB，可以设置 `FORCE_ADB=1`。

#### **房间 4：核心采集函数 `collect_system_info` —— 体检项目**
这是脚本的“心脏”，它在 **运行 rktop 前后各执行一次**，采集以下信息（每个项目都对应一段在板端远程执行的命令）：

1. **基础信息**：主机名、内核版本、开机时长、设备型号。
2. **CPU**：核心数、负载、每个核心的当前频率和工作模式，以及整体使用率。
3. **内存**：`free -m` 和 `/proc/meminfo` 中的关键项。
4. **温度**：所有 thermal zone 的温度（CPU、GPU、NPU 等），并找出最高温。
5. **NPU**：频率、驱动版本、负载、内存分配情况。这是 RK3588 的 AI 核心。
6. **GPU**：频率、利用率。
7. **磁盘**：分区使用率和 I/O 统计。
8. **进程**：CPU 和内存占用 Top 8 进程。
9. **DDR**：内存频率。

**初学者注意**：这些信息通过 `run_remote_script` 函数送到板端执行。你不用手动登录板子一条条敲，脚本全自动搞定。

#### **房间 5：主流程 —— 七步走**
1. **检测连接**：SSH 还是 ADB？
2. **检查 rktop**：确保板端 `/userdata/rktop` 存在。若没有，脚本会报错并提示用 `adb push` 推送。
3. **检查内核接口**：确认 `/sys/class/devfreq/fdab0000.npu` 等 NPU/GPU 节点存在，这是后续采集的基础。
4. **运行前快照**：调用 `collect_system_info "BEFORE"` 记录基线。
5. **启动 rktop**：通过 SSH 远程运行 `rktop`，并在你的终端上显示实时界面。它会一直跑，直到你按 `Ctrl+C` 或达到超时时间（默认 60 秒）。
6. **运行后快照**：调用 `collect_system_info "AFTER"` 记录负载下的状态。
7. **生成对比摘要**：把前后 CPU 负载、内存、温度峰值、NPU 频率放到一个表格里，一目了然。

### 三、初学者最关心的实操问题

#### **1. 我该怎么用？**
**第一步：把脚本传到你的电脑（Linux/WSL/Mac 均可）**，保存为 `test_rktop_on_board.sh`，并赋予执行权限：
```bash
chmod +x test_rktop_on_board.sh
```
**第二步：确保板端有 `rktop`**。通常你需要从 Rockchip 的 wiki 或 SDK 获取该二进制，然后 `adb push` 到 `/userdata/rktop`。
**第三步：配置好 SSH 免密登录**（推荐），或确保知道 root 密码。
**第四步：运行**：
```bash
./test_rktop_on_board.sh 你开发板的IP
```

#### **2. 运行中我会看到什么？**
- 终端会先打印一系列 `[STEP]` 信息，告诉你正在执行哪一步。
- 然后你会看到**运行前的系统信息**（CPU 频率、温度……）。
- **最关键的一步**：脚本会启动 `rktop`，你的终端会瞬间变成类似 `htop` 的实时监控画面，你可以直观地看到各模块负载。按 `Ctrl+C` 退出。
- 退出后，脚本自动采集“运行后”信息，并打出**对比表**。

#### **3. 脚本跑完，怎么找报告？**
所有输出都保存在 `/tmp/rktop_remote_test_日期时间.log`。你可以用 `less` 查看，或者 grep 关键词：
```bash
grep -E 'STEP|OK|ERROR|对比' /tmp/rktop_remote_test_*.log
```

#### **4. 我可能会遇到哪些坑？**
- **SSH 连接失败**：检查 IP、用户名，或者改用 `FORCE_ADB=1 ./test_rktop_on_board.sh` 强制 ADB 模式。
- **`rktop` 找不到**：脚本会明确提示 `未找到 /userdata/rktop`，按照提示推送文件即可。
- **采集信息为空**：内核接口路径可能因 Linux 版本而异。脚本已考虑了多个可能路径，但如果你的 BSP 较旧或较新，个别项可能显示 `N/A`，不影响整体流程。
- **ADB 模式无法直接显示 TUI**：脚本已处理这种情况，会提示你手动启动。

### 四、这个脚本对你有什么价值？

对于刚接触 RK3588 的你，它有三重意义：

1. **一键体检**：不用再分别敲 `free`、`cat /sys/...` 等 10 多条命令，一个脚本全搞定。
2. **性能对比利器**：比如你想知道运行 AI 模型前后 NPU 频率和温度的变化，直接跑两次脚本（一次空载、一次运行模型），对比报告就能告诉你。
3. **学习 Shell 编程的范本**：脚本结构清晰，函数封装、日志、错误处理、远程执行、环境变量等手法都相当规范，是初学者进阶的绝佳参考。

简单说，它就是你在 RK3588 上的“性能体检师”，让你从枯燥的手工命令中解脱出来，把精力放在真正的性能优化上。

`rktop` 对于 RK3588 上的 AI 性能调优，就像你驾驶赛车时的**实时仪表盘**。

它本身不能直接帮你加速，但没了它，你根本不知道引擎（NPU/CPU）有没有出力、轮胎（内存带宽）有没有打滑、水温（温度）有没有过高。

下面是它在嵌入式AI开发中的具体价值：

### 1. 它是“异构计算”的任务管理器
与电脑上只能看CPU的`htop`不同，**RK3588 是“CPU+GPU+NPU+RGA”的四驱异构芯片**。运行AI模型时，往往是多个单元协同工作。`rktop` 能在一个屏幕上同时显示所有这些模块的**实时利用率、频率**。

- **实战场景**：你跑了一个视觉-语言模型（VLM），发现推理很慢。打开 `rktop`，如果看到**NPU利用率90%以上**，说明瓶颈在算力；如果**NPU利用率很低**，但CPU很高，那说明模型可能没跑在NPU上，或者预处理成了瓶颈。这一步就能帮你**确定优化的大方向**。

### 2. 它是分析“温度墙”的必备工具
嵌入式的性能波动，40%的原因是散热降频。RK3588 在无主动散热下，NPU全速运行几分钟就会撞到温度墙并降频。

- **实战场景**：你用 `rknn-smi` 或 `perf` 发现推理速度时快时慢。打开 `rktop` 盯着温度看，如果推理慢的时候，温度冲到了**85°C以上**，且NPU频率突然从1GHz掉到600MHz，那你的优化方向就不是改模型，而是**加强散热**或在软件上做**功耗控制**。

### 3. 它是“离线部署”的工程神器
很多设备在产线或现场没有屏幕，只有SSH远程登录。`rktop` 是一个**极其轻量的终端UI**，无需桌面环境，通过 `ssh -t` 就能远程打开，就像在现场看仪表盘一样。这也是为什么前一个脚本花了大量功夫远程启动它并采集数据。

**一句话总结**：
**`rktop` 不是精准的手术刀（那是 `RKNN Toolkit` 和 `perf` 的角色），但它是最快的听诊器。它能让你一眼看清系统当前的“健康状态”，决定下一步该去查代码、调模型、还是加风扇。**
