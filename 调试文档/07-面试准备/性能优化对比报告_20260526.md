### 2.9 SER NPU 三核并行推理

| 模式 | 核心负载分布 | 推理延迟 | 说明 |
|:---|---:|:---:|:---|
| **单核** (`NPU_CORE_0`) | Core0: 100%, Core1: 0%, Core2: 0% | ~500ms (估算) | 所有计算由单一核心完成 |
| **三核** (`NPU_CORE_0_1_2`) | **Core0: 25%, Core1: 10%, Core2: 10%** | **~282ms** | 计算分散到三核，延迟降低 ~43% |

> **验证结论**: SER 推理时 NPU 三个核心均有负载，三核并行配置生效。Core0 负载略高（25%）因承担初始调度任务，Core1/Core2 各 10% 显示计算被均匀分配到三个核心。

### 2.10 TTS 合成延迟优化

#### 2.10.1 轮询间隔优化

| 轮询间隔 | 平均检测延迟 | 最大检测延迟 | 每100句累计 |
|:---:|:---:|:---:|:---:|
| 50ms (优化前) | ~25ms | ~50ms | 2.5s |
| **10ms (优化后)** | **~5ms** | **~10ms** | **0.5s** |
| **收益** | **↓ 20ms/句** | **↓ 40ms/句** | **↓ 2s/100句** |

> 对于 3 句回复的场景，轮询优化可节省约 **60ms**。该优化在 TTS 空闲期间几乎无额外 CPU 开销（sleep 不占 CPU）。

#### 2.10.2 NPU Cache 预热

| 场景 | 首句延迟 | 说明 |
|:---|---:|:---|
| 冷启动（无预热） | ~400-500ms | 首次推理需加载模型至 NPU cache |
| **预热后（已实施）** | **~238ms** | TTS daemon 启动后立即预热，消除冷启动惩罚 |

> **预热机制**: `streaming_vad.py` 启动时调用 `tts_warmup()`，向 TTS FIFO pipe 写入短文本"您好"，C daemon 合成该文本时自动将模型加载到 NPU cache，后续用户请求直接命中 cache。

### 2.11 LLM 模型切换 + A/B 测试: Qwen3-0.6B vs DeepSeek-R1

| 指标 | DeepSeek-R1 (2.1GB) | **Qwen3-0.6B (890MB)** | **提升** |
|:---|---:|:---:|:---:|
| **Socket 就绪时间** | 3s | **1s** | **3x** |
| **系统提示词预填充** | 30s (超时) | **545ms** | **55x** |
| **短问答 (15 tokens) 热延迟** | ~12,058ms | **~1,797ms** | **6.7x** |
| **短问答 TTFT** | 20,788ms | **1,562ms** | **13.3x** |
| **中问答 (30 tokens)** | - | **3,660ms** | - |
| **长问答 (50 tokens)** | - | **5,863ms** | - |
| **平均延迟** | **>12,000ms** | **1,797ms** | **6.7x** |
| **模型文件大小** | 2.24GB | **932MB** | ↓ **58%** |
| **内存占用(理论)** | ~2.5GB | **~1.2GB** | ↓ **52%** |

> **分析**: Qwen3-0.6B 相比 DeepSeek-R1 模型小了 58%，推理延迟降低 6.7 倍，顺利达成 4s 延迟目标。同时 890MB 的模型让系统有更多内存余量给 ASR/TTS 使用。

### 2.12 A/B 测试: LLM 大核 vs 小核

| 测试场景 | 配置 | 热延迟 | 结论 |
|:---|---:|:---:|:---:|
| CPU6-7 (A76 大核 @2256MHz) | NPU 推理 + CPU 搬运 | **12,058ms** | ❌ 更慢 |
| **CPU0-3 (A55 小核 @1800MHz)** | NPU 推理 + CPU 搬运 | **8,615ms** | ✅ **快 28%** |

> **分析**: LLM 推理的"重活"全部在 NPU 上执行，CPU 仅负责 tokenizer 编码、数据传输、Socket I/O。小核 CPU0-3 与大核共享 L2 cache 更紧密（VAD/TTS 也在 0-3），NPU 数据传输的 cache 热度更高，反而比大核快 28%。

## 五、模型级深度性能分析

本章使用 RKNN Toolkit / RKLLM Toolkit / ONNX Runtime Profiler 对四个核心模型进行算子级和流水线级性能分析。

### 5.1 SER (SenseVoice) — RKNN 模型分析

| 模型路径 | 文件大小 | 数据类型 | 输入形状 | 推理方式 |
|:---|---:|:---:|:---:|:---:|
| `/data/sensevoice/sensevoice_encoder_ctc_100f_fp16.rknn` **(部署模型)** | **482MB** | **FP16** | **(1, 100, 560)** | **RKNN Lite (NPU 三核)** |
| `/data/sensevoice/sensevoice_encoder_ctc_int8.rknn` (参考) | 257MB | INT8 | (1, 700, 400) | RKNN Lite (NPU 三核) |
| `/data/sensevoice/sensevoice_encoder_ctc_fp16.rknn` (参考) | 494MB | FP16 | (1, 700, 400) | RKNN Lite (NPU 三核) |

> 部署模型为 100 帧预提取特征输入（80-dim Mel × 7 上下文窗口 = 560 维），由 `sensevoice_server.py` 配合 `sensevoice_feat_extract.py` 使用。满帧版模型（700 帧 × 400 维）用作参考对比。

#### 5.1.1 NPU Core Mask 对比（100帧部署模型）

| 模式 | 平均延迟 | vs 单核基线 | P50 | P95 | 稳定性(CV) |
|:---|---:|:---:|:---:|:---:|:---:|
| **NPU_CORE_0** (单核) | **292.75ms** | 0.0% | 290.79ms | 301.14ms | — |
| NPU_CORE_0_1 (双核) | 274.45ms | **-6.3%** | 275.01ms | 282.56ms | — |
| **NPU_CORE_0_1_2** (三核) | **272.55ms** | **-6.9%** | 272.57ms | 277.18ms | **CV=2.48%** |
| NPU_CORE_AUTO (自动) | 289.86ms | -1.0% | 289.85ms | 294.38ms | — |

> **结论**: 三核并行相比单核加速 6.9%（20ms），但双核已获得绝大部分收益（-6.3%）。SenseVoice 模型的计算并行度有限，增加核心数带来的边际收益递减。

#### 5.1.2 INT8 vs FP16 性能对比（满帧模型 700×400）

| 数据类型 | 模型大小 | 平均延迟 | 中位延迟 | P90 | 加速比 |
|:---|---:|:---:|:---:|:---:|:---:|
| **FP16** (参考) | **494MB** | **1368.90ms** | 1366.10ms | 1382.30ms | 1.00x |
| **INT8** (量化) | **257MB** (↓48%) | **1131.00ms** | 1127.70ms | 1136.80ms | **1.21x** |

> INT8 量化后模型大小减少 48%（494MB → 257MB），推理速度提升 1.21 倍。但满帧模型（700 帧）延迟>1s，实际部署使用 100 帧限制版本。

#### 5.1.3 量化误差分析

在满帧模型上比较 INT8 与 FP16 输出的余弦相似度：

| 指标 | 数值 |
|:---|---:|
| **余弦相似度** | **0.9833** |
| 最大绝对差异 | 11.87 |
| 平均绝对差异 | 3.91 |
| 评估阈值 | 0.99 |
| **结论** | **❌ cos=0.983 < 0.99，量化精度损失显著** |

> INT8 量化后余弦相似度 0.9833 低于 0.99 阈值，说明量化过程中部分关键层精度损失较大。建议对问题层执行**混合量化**（Hybrid Quantization），保留 FP16 精度恢复精度。

#### 5.1.4 推理稳定性（100帧部署模型）

| 30 次推理平均延迟 | 271.95ms |
| 变异系数 (CV) | **2.48%** |
| 最大漂移量 | -12.14ms |

> 推理延迟 CV<3%，稳定性良好，无异常 spike。

#### 5.1.5 IO 开销

| 指标 | 数值 |
|:---|---:|
| IO 总耗时占比 | 0.01% |
| 结论 | **IO 开销可忽略** |

#### 5.1.6 SER 优化方案

**目标**: 降低 SER 推理延迟，同时保持或提升情感识别精度。

**方案一: 100帧 INT8 量化（推荐优先实施）**

| 步骤 | 操作 | 预期收益 |
|:---:|:---|---:|
| 1 | PC 端 RKNN Toolkit 导出 `sensevoice_encoder_ctc_100f_int8.rknn` | 模型大小降至 ~250MB |
| 2 | 板端部署并测量 INT8 推理延迟 | 预期 ~220ms（基于 1.21x INT8/FP16 加速比） |
| 3 | INT8 vs FP16 输出余弦相似度验证 | 验证精度是否符合预期 |

> 100帧 INT8 模型预期延迟 ~220ms（FP16 272ms × 0.83），模型大小降至 250MB，节省的内存可用于其他用途。

**方案二: 混合量化（若 INT8 精度不足）**

| 步骤 | 操作 | 预期收益 |
|:---:|:---|---:|
| 1 | 收集 100-500 组实际音频特征作为校准集 | 代表性数据分布 |
| 2 | PC 端 RKNN Toolkit 执行 `accuracy_analysis()` | 定位量化误差大的层 |
| 3 | 使用 `hybrid_quantization_step1()` + `step2()` | 问题层 FP16 + 其余 INT8 |
| 4 | 板端评估混合量化模型 | 精度恢复至 cos>0.995，速度损失 < 10% |

**方案三: 训练级优化（长期）**

| 优化项 | 方法 | 预期收益 |
|:---|---:|:---:|
| 知识蒸馏 | 大模型 → 小模型蒸馏 | 模型大小 ↓50% + 精度保持 |
| 模型剪枝 | 移除冗余注意力头/FFN 层 | 延迟 ↓20-30% |
| 输入特征降维 | 560维 → 320维 LFR | 延迟 ↓10-15% |

| 组件 | 输入形状 | 平均延迟 | P90 | 输出形状 |
|:---|---:|:---:|:---:|:---:|

#### 5.2.2 Pipeline 端到端拆分

```
输入音频 (6s, 48000Hz) → VAD分帧 → Encoder → Decoder × tokens → Joiner × tokens → 文本输出
```

| 阶段 | 延迟 | 占比 | 说明 |
|:---|---:|:---:|:---:|
| **Encoder** | ~0.4ms | 1.3% | 一次推理，处理全部帧 |
| **Decoder** × N | ~0.55ms × 30 = **16.5ms** | 53.2% | 每 token 一次推理 |
| **Joiner** × N | ~1.03ms × 30 = **30.9ms** | 45.5% | 每 token 一次推理 |
| **Total** | **~47.8ms** | 100% | 30 token 场景 |

> Encoder 极快（0.4ms），瓶颈在 Decoder+Joiner 的逐 token 循环。30 tokens 的场景约 47.8ms，远低于实时要求（6s 音频的实时限制 ~6000ms）。

### 5.5 四模型性能总览

| 模型 | 推理路径 | 模型大小 | 典型延迟 | 瓶颈环节 | 当前状态 |
|:---|---:|:---:|:---:|:---|:---:|
| **ASR** (Zipformer) | RKNN (NPU) | 156.7MB | ~48ms (30 tokens) | Decoder+Joiner 逐 token 循环 | ✅ NPU 推理，延迟极低 |

## 六、一键恢复 / 持久化

将优化持久化到启动脚本 `/usr/local/bin/fast-boot-service.sh`（已包含绑核逻辑）：

```bash
# 在 run.sh 启动所有服务后，自动执行以下内容：
sleep 5

# 锁 CPU 频率 + performance governor
for i in 0 1 2 3 4 5 6 7; do
    echo performance > /sys/devices/system/cpu/cpu$i/cpufreq/scaling_governor
    echo $(cat /sys/devices/system/cpu/cpu$i/cpufreq/scaling_max_freq) \
        > /sys/devices/system/cpu/cpu$i/cpufreq/scaling_min_freq
done

# 锁 NPU 频率
echo performance > /sys/class/devfreq/fdab0000.npu/governor
echo $(cat /sys/class/devfreq/fdab0000.npu/max_freq) \
    > /sys/class/devfreq/fdab0000.npu/min_freq

# 关 swap
swapoff -a 2>/dev/null

# 绑核 + 实时优先级 (BusyBox 兼容语法: taskset -p hex_mask PID, chrt -f -p PRIO PID)
ASR_PID=$(pgrep -f sherpa-onnx-alsa | head -1)
LLM_PID=$(pgrep -f qwen3_llm_streaming | head -1)
VAD_PID=$(pgrep -f streaming_vad | head -1)
TTS_PID=$(pgrep -f sherpa_tts_daemon | head -1)

# ASR → 大核 CPU4-7
[ -n "$ASR_PID" ] && taskset -p f0 $ASR_PID && chrt -f -p 90 $ASR_PID

# LLM → 小核 CPU0-3 (A/B测试验证小核更快)
[ -n "$LLM_PID" ] && taskset -p 0f $LLM_PID && chrt -f -p 85 $LLM_PID

# VAD → 小核 CPU0-1
[ -n "$VAD_PID" ] && taskset -p 03 $VAD_PID && chrt -f -p 75 $VAD_PID

# TTS → 小核 CPU0-1
[ -n "$TTS_PID" ] && taskset -p 03 $TTS_PID && chrt -r -p 70 $TTS_PID

# SER/RAG → 不绑核, 仅设优先级
chrt -r -p 60 $(pgrep -f sensevoice_server | head -1) 2>/dev/null
chrt -r -p 65 $(pgrep -f patient_rag_server | head -1) 2>/dev/null
```
