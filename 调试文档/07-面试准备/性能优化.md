## 一、工具检测原理：如何发现优化点

### 1.1 问题：`--num-threads=-4` 参数错误

**检测工具**：`ps aux | grep sherpa-onnx`

```
root 2406 ... sherpa-onnx-alsa --num-threads=-4 ...
```

**发现过程**：直接查看进程命令行发现参数值为 `-4`（负数），这是明显错误。

**为什么这是个问题**：

```
sherpa-onnx-alsa 的 --num-threads 参数指定 CPU 线程数
-4 会被 C++ 端解释为无效值，导致线程池初始化异常
→ 表现为 CPU 轮询效率低下（perf top 验证 CPU 占用 48.20%）
→ ASR 推理延迟从预期的 ~250ms 变为 ~386ms
```

**根因**：`streaming_vad.py` 中写死了 `--num-threads=-4`，可能是笔误。

---

### 1.2 问题：CPU 频率未达到最大值

**检测工具**：`/sys/devices/system/cpu/cpu*/cpufreq/scaling_cur_freq`

```
cpu0: 1200 MHz（最大 1800 MHz，利用率 67%）
cpu4: 1200 MHz（最大 2352 MHz，利用率 51%）
cpu6: 1416 MHz（最大 2256 MHz，利用率 63%）
```

**发现过程**：对比当前频率和最大频率，发现 CPU 运行在远低于最大值的频率上。

**为什么这是个问题**：

```
schedutil 是动态调频策略，根据 CPU 负载自动升降频
当 VAD 静默期 CPU 空闲时，频率降到 408 MHz
突然有语音输入时，升频需要 10-50ms 响应时间
→ 这 10-50ms 加到了端到端延迟中
```

---

### 1.3 问题：NPU 满载但无异常

**检测工具**：`/sys/class/devfreq/fdab0000.npu/load`

```
cat /sys/class/devfreq/fdab0000.npu/load
100@1000000000Hz
```

**发现过程**：读取 NPU 负载文件显示 100% 负载，频率为 1.0 GHz。

**为什么这是个好现象**：

```
NPU 利用率 100%，说明 LLM 推理完全跑在 NPU 上
频率 1.0 GHz 已经是最高（available_frequencies 确认最大值）
→ 验证 NPU 已充分使用，不是瓶颈
→ 优化方向应转向内存带宽或模型压缩
```

---

### 1.4 问题：所有进程共享全部 CPU 核心

**检测工具**：`taskset -p <PID>`

```
PID 1258 (streaming_vad): mask=ff（所有 8 核）
PID 1276 (LLM service):  mask=ff（所有 8 核）
PID 1318 (SER service):  mask=ff（所有 8 核）
PID 1302 (TTS daemon):   mask=ff（所有 8 核）
```

**发现过程**：所有进程的 CPU 亲和性掩码都是 `ff`（11111111），即都允许在任意核心上运行。

**为什么这是个问题**：

```
一个进程在不同核心间切换会带来缓存失效（cache miss）
TTS（CPU ONNX 推理）和 LLM（Python 主线程）在同一个核心上争抢
大核（A76）跑轻量任务（如音频播放）是资源浪费
→ 通过核心绑定可以隔离负载，减少缓存抖动
```

---

### 1.5 问题：TTS 线程数设置偏低

**检测工具**：`grep -rn 'num_threads' /data/voice_assistant/`

```python
# matcha_tts_service.py
session_opts.intra_op_num_threads = 2
```

**发现过程**：查看 TTS 服务源码发现 intra_op_num_threads 设为 2。

**为什么这是个问题**：

```
RK3588 有 4 个 A76 大核
Matcha-TTS 是 CPU ONNX 推理，可以并行
线程数 2→4 理论上可以提升约 1.5-1.8 倍推理速度
→ 从 ~600ms 降至 ~350ms
```

---

### 1.6 问题：无实时优先级

**检测工具**：`chrt -p <PID>`

```
PID 1258: SCHED_OTHER (priority=0)
PID 2406: SCHED_OTHER (priority=0)
```

**发现过程**：所有进程都是默认的普通调度策略和优先级。

**为什么这是个问题**：

```
语音助手对音频路径的实时性要求高
VAD → ASR → LLM → TTS → 播放 的整条链路需要确定性的调度延迟
虽然 cyclictest 显示 Max=15µs 已经很好
但给关键路径设 FIFO 优先级可以进一步消除抖动
```

### 1.7 确认：实时性表现极好

**检测工具**：`cyclictest`

```
空载: Min=4µs, Avg=5µs, Max=15µs
满载(stress 4核+IO+内存): Min=5µs, Avg=9µs, Max=15µs
```

**发现过程**：在不同负载条件下运行 cyclictest，测量调度延迟。

**为什么这是个好消息**：

```
Max=15µs 意味着最坏情况下调度延迟仅 15 微秒
对比：语音助手的 VAD 超时是 800ms，TTS 播放周期是 ~23ms（48kHz/帧）
15µs 远远小于这些阈值，不会造成音频卡顿
→ 说明 RK3588 即使没有 RT 内核补丁，实时性也已足够
```

soc-thermal: 36.1°C

### 2.2 `/sys` 文件系统 — 设备频率和温度

```bash
# CPU 频率
cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_cur_freq   # 当前频率
cat /sys/devices/system/cpu/cpu0/cpufreq/cpuinfo_max_freq   # 最大频率
cat /sys/devices/system/cpu/cpu0/cpufreq/scaling_governor   # 调频策略

# CPU 可用频率列表
cat /sys/devices/system/cpu/cpufreq/policy0/scaling_available_frequencies
cat /sys/devices/system/cpu/cpufreq/policy4/scaling_available_frequencies

# NPU 频率和负载
cat /sys/class/devfreq/fdab0000.npu/cur_freq                # NPU 当前频率
cat /sys/class/devfreq/fdab0000.npu/available_frequencies   # NPU 可用频率
cat /sys/class/devfreq/fdab0000.npu/load                    # NPU 实时负载
cat /sys/class/devfreq/fdab0000.npu/governor                # NPU 调频策略
cat /sys/class/devfreq/fdab0000.npu/trans_stat              # 频率切换统计

# DDR 频率
cat /sys/class/devfreq/dmc/cur_freq
cat /sys/class/devfreq/dmc/available_frequencies

# 温度
cat /sys/class/thermal/thermal_zone0/temp                   # 除以1000得°C

# 一键查看所有温度
for z in /sys/class/thermal/thermal_zone*; do
  echo "$(cat $z/type): $(cat $z/temp | awk '{printf "%.1f°C", $1/1000}')"
done
```

**面试问法**：RK3588 上如何查看 NPU 的实时利用率和频率？

---

### 2.3 `taskset` — CPU 亲和性

```bash
# 查看进程的 CPU 亲和性
taskset -p <PID>

# 设置进程绑定到特定核心
taskset -p 0x0f <PID>   # 绑定到 CPU 0-3 (小核)
taskset -p 0xf0 <PID>   # 绑定到 CPU 4-7 (大核)
taskset -p 0x30 <PID>   # 绑定到 CPU 4-5

# 启动时绑定
taskset -c 0-3 python3 my_service.py
```

**面试问法**：为什么要做 CPU 核心绑定？有什么好处？

**答案要点**：
- 减少缓存miss（cache affinity）
- 避免进程在不同核心间频繁切换的开销
- 隔离计算密集型任务和 I/O 任务
- 在大小核架构上合理分配负载

---

### 2.4 `chrt` — 实时优先级

```bash
# 查看进程调度策略和优先级
chrt -p <PID>

# 设置为 FIFO 实时调度，优先级 50
chrt -f -p 50 <PID>

# 设置为 RR 轮转实时调度
chrt -r -p 50 <PID>

# 各类调度策略
SCHED_OTHER  # 默认，普通分时
SCHED_FIFO   # 实时，先入先出，直到主动放弃CPU
SCHED_RR     # 实时，轮转，时间片用完自动切换
SCHED_BATCH  # 批处理，适合CPU密集型
SCHED_IDLE   # 空闲，极低优先级
```

**面试问法**：SCHED_FIFO 和 SCHED_RR 有什么区别？

**答案要点**：
- FIFO：同优先级先到先执行，除非被更高优先级抢占或主动让出，否则一直运行
- RR：同优先级按时间片轮转，每个进程运行固定时间片后切换到下一个
- FIFO 适合确定性延迟要求高的场景，RR 适合同优先级需要公平调度的场景

---

### 2.5 `perf` — CPU 性能采样

```bash
# 实时查看 CPU 热点（按进程排序）
perf top --sort comm

# 按符号（函数名）排序
perf top --sort symbol

# 采样并生成报告
perf record -g -p <PID> -- sleep 10   # 采集10秒
perf report                            # 生成报告

# 查看指定 CPU 热点
perf top -C 0-3                       # 只看小核

# 查看内核态热点
perf top -k
```

**面试问法**：perf 的工作原理是什么？

**答案要点**：
- 基于硬件 PMU（Performance Monitoring Unit）的采样
- 以固定频率触发中断，记录当前执行的指令地址/函数名
- 统计各函数被采样到的次数占比，推断 CPU 时间分布
- 采样频率通过 -F 参数控制（如 4000Hz）
- 缺点：采样是近似统计，低频采样可能错过短时热点

---

### 2.6 `cyclictest` — 实时性测试

```bash
# 基本测试（30次循环，锁定内存，FIFO优先级95，间隔1000µs）
cyclictest -l 30 -m -p 95 --policy=fifo -i 1000

# 配合 stress 做压力测试
stress -c 4 -i 2 -m 1 --vm-bytes 256M &
cyclictest -l 100 -m -p 95 --policy=fifo -i 1000
kill %1

# 输出解读
# T: 0 (线程号) P:95 (优先级) I:1000 (间隔µs) C:30 (循环数)
# Min:4 (最小延迟µs) Act:14 (当前延迟) Avg:5 (平均) Max:15 (最大)
```

**面试问法**：cyclictest 的 Min/Act/Avg/Max 各代表什么？

**答案要点**：
- Min：最小延迟，接近硬件中断响应极限
- Act：最近一次测量的延迟
- Avg：平均延迟，反映整体性能
- Max：最大延迟（最差情况），是实时性的关键指标
- 实时系统通常关注 Max 值是否在 deadline 范围内

---

### 2.7 `stress` / `stress-ng` — 压力测试

```bash
# CPU 压力：4 个 worker 计算平方根
stress -c 4

# 内存压力：分配并频繁读写 256MB
stress -m 1 --vm-bytes 256M

# I/O 压力：2 个 worker 执行 sync
stress -i 2

# 综合压力
stress -c 4 -i 2 -m 2 --vm-bytes 512M

# 更强大的 stress-ng（如已安装）
stress-ng --cpu 4 --io 2 --vm 2 --vm-bytes 256M --timeout 30s
```

## 三、高频面试题

### 3.1 基础概念类

#### Q1: RK3588 的异构计算架构是什么样的？

RK3588 采用 **big.LITTLE 大小核 + 独立 NPU** 架构：

- **4x Cortex-A76 (大核)**：性能核心，适合繁重计算，最高 2.4GHz
- **4x Cortex-A55 (小核)**：效率核心，适合轻量后台任务，最高 1.8GHz
- **NPU (神经网络处理器)**：3 核心设计，支持 INT4/INT8/FP16，最高 6 TOPS
- **Mali-G610 GPU**：图形加速，但不适合通用计算（驱动不完善）
- **DMC (动态内存控制器)**：DDR 频率影响整体瓶颈

**面试考点**：大小核架构的调度策略、NPU 与 CPU 的协同工作方式。

---

#### Q2: 端侧 AI 部署和云端 AI 部署有什么区别？

| 维度 | 端侧 | 云端 |
| :--- | :--- | :--- |
| 计算资源 | 有限（4-8GB内存，NPU 6TOPS） | 几乎无限 |
| 模型大小 | 需量化压缩（<2GB） | 可运行百亿参数模型 |
| 延迟要求 | 实时（<4秒） | 可容忍秒级 |
| 网络依赖 | 离线运行 | 依赖网络 |
| 功耗限制 | 严格（几瓦） | 宽松 |
| 工具链成熟度 | 碎片化 | 成熟（CUDA/TensorRT） |
| 数据隐私 | 数据不出设备 | 需上传服务器 |

**面试考点**：理解端侧部署的核心挑战（资源受限、工具链不成熟）。

---

#### Q3: 什么是模型量化？w4a16 和 w8a8 有什么区别？

模型量化是将模型参数从高精度（FP32/FP16）压缩到低精度（INT8/INT4）的技术。

| 量化方案 | 权重 | 激活值 | 模型缩小比 | 精度损失 |
| :--- | :--- | :--- | :--- | :--- |
| w8a8 | INT8 | INT8 | ~4x vs FP32 | 较小 |
| w4a16 | INT4 | FP16 | ~4x vs FP32 | 中等 |
| w4a8 | INT4 | INT8 | ~8x vs FP32 | 较大 |

**DeepSeek-R1-CMtMedQA 当前使用 w8a8**：模型从原始 ~8GB 压缩到 2.1GB。

**面试考点**：量化对推理速度、内存占用、精度的影响，W4A16 的部署收益。

### 3.2 工具使用类

#### Q4: 如何判断 RK3588 上的 NPU 是否被正确调用？

**方法一：检查进程和参数**

```bash
# 确认模型文件是 .rknn 格式（NPU 模型）
ls -la /data/zipformer/model/*.rknn

# 确认推理库使用 rknn 后端
ps aux | grep rknn

# 检查进程是否加载了 rknn 相关库
cat /proc/<PID>/maps | grep rknn
```

**方法二：监控 NPU 频率和负载**

```bash
# 在推理时 NPU 频率应升到最高
watch -n 1 cat /sys/class/devfreq/fdab0000.npu/load

# 如果 load 始终为 0 或很低 → NPU 没被调用
# 如果 load 显示 100% → NPU 正在全力工作
```

**方法三：对比推理速度**

```
CPU 推理 LLM：通常 < 5 t/s（tokens/秒）
NPU 推理 LLM：通常 > 10 t/s
如速度仅 2-3 t/s，可能未正确使用 NPU
```

**面试考点**：不只是看模型格式，还要验证运行时 NPU 确实在工作。

---

#### Q5: perf top 结果显示 sherpa-onnx-alsa 占用 48% CPU，这正常吗？

**分析过程**：

```
1. sherpa-onnx-alsa 是 ASR 服务，使用 Zipformer RKNN 模型
2. Zipformer 的编码器/解码器/连接器跑在 NPU 上
3. 但数据预处理、后处理、音频采集仍在 CPU 上
4. 48% CPU 说明 CPU 部分的开销较大
5. 进一步排查发现 --num-threads=-4 参数错误
6. 修正后预期 CPU 占用可降至 ~20%
```

**面试考点**：系统思维——不能只看表面数字，要理解 CPU/GPU/NPU 的协同关系。

---

#### Q6: 如何定位端到端延迟的瓶颈？

**流水线分段计时法**：

```python
# 在代码中插入时间戳
t0 = time.time()
# VAD 检测到语音结束

t1 = time.time()
vad_delay = t1 - t0
# ASR 识别完成

t2 = time.time()
asr_delay = t2 - t1
# LLM 推理出第一句话

t3 = time.time()
llm_first_sentence_delay = t3 - t2
# TTS 合成完成

t4 = time.time()
tts_delay = t4 - t3

total_delay = t4 - t0
```

**每个阶段的优化空间**：

| 阶段 | 基准延迟 | 优化方向 |
| :--- | :--- | :--- |
| VAD | 300-800ms | 减少尾部静音阈值 |
| ASR | 200-500ms | 修复线程参数、PTY缓冲 |
| LLM | 400-2000ms | 模型量化、减小模型、预填充KV Cache |
| TTS | 100-600ms | 增加线程数、C daemon |

**面试考点**：端到端思维，知道每个阶段的可优化空间。

### 3.3 优化策略类

#### Q7: 为什么端侧 LLM 部署需要预填充（Prefill）KV Cache？

**原理**：
- Transformer 推理时，每个 token 需要计算 Key 和 Value
- System Prompt（如"作为医疗助手，简短回答"）的内容固定不变
- 预填充：在加载模型时，提前将 System Prompt 的 KV Cache 算好存入 NPU 内存

**为什么重要**：
- 每次推理无需重复计算 System Prompt → **节省 30-50% 推理时间**
- 对于 DeepSeek-R1-CMtMedQA，System Prompt 较短，收益不如长上下文场景明显
- 但在 RK3588 内存有限的环境下，预填充减少的内存访问依然有价值

**面试考点**：理解 Transformer 的 KV Cache 机制和内存优化。

#### Q8: 如何在边缘设备上权衡模型大小和推理质量？

3. **精度需求**：医疗场景需保证回答准确性

#### Q9: 什么是算子融合（Operator Fusion）？在端侧部署中有什么作用？

**算子融合**是将多个连续的计算操作合并为一个操作的技术。

**举例**：

```
融合前：Conv2D → BatchNorm → ReLU → Add
        4次内存读写 + 4次Kernel启动

融合后：Conv2D+BatchNorm+ReLU+Add（单算子）
        1次内存读写 + 1次Kernel启动
```

**在 RK3588 上的作用**：

```
1. 减少 NPU 的 Kernel 启动开销（每次启动 ~10-50µs）
2. 减少中间结果的内存读写（DDR 带宽是主要瓶颈）
3. RKNN Toolkit 的 optimization_level=3 自动启用算子融合
```

**面试考点**：理解算子融合为什么在端侧比在云端更重要（端侧内存带宽更有限）。

### Q11: 你们这个项目为什么从 MeloTTS 切换到 Matcha-TTS？

**背景**：MeloTTS 最初用 RKNN 在 NPU 上推理，但遇到 decoder 的 y_mask 与 rknn_lite API 不兼容问题，导致输出恒定噪声。

**切换过程**：

```
MeloTTS（RKNN NPU） → 问题：y_mask兼容性、输出噪声
  ↓
Paroli TTS（CPU ONNX） → 问题：合成慢，单次 4.3 秒
  ↓
Matcha-TTS（C daemon + FIFO pipe） → 问题解决
```

**Matcha-TTS 优势**：
- C 语言 daemon 常驻，无 Python 调度开销
- FIFO pipe 通信，流式播放
- 合成延迟从 4.3 秒降到 ~100ms（首句合成）
- 支持 Lexicon 词典定制（医疗术语发音）

### Q12: 你们是如何解决 ASR 管道 10-58 秒超长延迟的？

**问题**：sherpa-onnx-alsa 的 stderr 输出在 pipe 模式下使用 Glibc 全缓冲（4KB/8KB），导致识别结果要等缓冲区满了才一次性输出。

**解决方案**：

```
第一步（PTY 伪终端）：
   用 pty.openpty() 创建伪终端
   让 C 程序以为自己在写终端 → 行缓冲
   识别结果逐行输出，不再积压

第二步（os.read 裸读）：
   避免 Python readline 的二次缓冲
   os.read(fd, 4096) 直接读取原始字节流

第三步（800ms 空闲超时）：
   数据流结束后等待 800ms
   没有新数据 → 判定语音结束
```

**效果**：延迟从 10-58 秒降到 ~386ms。

### Q15: RK3588 的 NPU 和 NVIDIA GPU 在 AI 部署上有什么本质区别？

| 维度 | RK3588 NPU | NVIDIA GPU (Jetson) |
| :--- | :--- | :--- |
| 架构 | 专用 ASIC，固定计算管线 | 通用并行处理器 |

**核心结论**：RK3588 NPU 适合固定模型的推理部署，不适合研究和实验；NVIDIA 适合需要灵活性和生态支持的场景。

### Q17: 什么是 Bigram Jaccard 相似度？为什么用在 RAG 中？

**Bigram（2-gram）**：将文本按两个字符一组切分。

```
"高血压" → {"高血", "血压"}
"高血压病" → {"高血", "血压",  "压病"}
```

**Jaccard 相似度**：两个集合的交集大小除以并集大小。

```
J("高血压", "高血压病") = |{高血, 血压}| / |{高血, 血压, 压病}|
                        = 2 / 3 = 0.667
```

**为什么选 Bigram 而不是词嵌入**：

```
在端侧部署中：
- 词嵌入模型（如 BERT）需要额外的模型加载和推理 → 增加内存和延迟
- Bigram Jaccard 不需要任何模型，纯字符串运算
- 对中文医疗短文本（症状、疾病名）匹配效果好
- 计算复杂度 O(n*m)，n/m 仅为几十，非常快
```

**优化**：统一数字格式（"35"→"三十五"）解决 Bigram 无法匹配数字格式的问题。
