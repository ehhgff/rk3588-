## 各优化详细说明

### 1. 时序埋点（TIMING）

在全局添加 `TIMING = {}` 字典，记录以下 7 个关键时间戳（均从说话结束时刻计算）：

| 时间戳 | 含义 |
|-------|------|
| `speech_end` | VAD 检测到语音结束 |
| `asr_done` | ASR 识别完成 |
| `rag_done` | RAG 检索完成 |
| `llm_first_sentence` | LLM 流式输出第一个句子到达 |
| `llm_done` | LLM 全部生成完成 |
| `tts_first_chunk_done` | 首句 TTS 合成完成 |
| `play_start` | aplay 开始播放 |

在 `streaming_vad.py` 末尾输出格式化的时序表格。

### 2. VAD 静音阈值 0.7s → 0.5s

```
SILENCE_FRAMES_THRESHOLD = int(0.5 / (FRAME_DURATION_MS / 1000))
```

减少录音结束后的静音等待时间，更快进入 ASR 阶段。

### 3. Drain loop 2.0s → 0.5s

`record_on_voice_detection()` 的 `finally` 块中录音停止后的额外缓冲区处理时间：

```python
end_time = time.time() + 0.5  # 原来是 2.0
```

### 4. TTS 速度 0.6 → 0.7

```python
def tts_synthesize(text, output, speed=0.7):  # 原来是 0.6
```

### 5. TTS 模型预热（启动时）

- 新增 `tts_warmup()` 函数，在启动时（VAD 监听前）调用
- 向 MeloTTS 服务发送一个句号"。"的合成请求，提前加载模型到 NPU
- 预热不占用用户感知的流水线时间

### 6. FIFO 流式播放

`play_audio()` 使用 `os.mkfifo` 创建命名管道，aplay 消费 FIFO 的同时 TTS 写入，实现边合成边播放。

```python
os.mkfifo(fifo_path)
aplay_proc = subprocess.Popen(["aplay", "-D", PLAY_DEVICE, "-r", str(rate), ...])
with open(fifo_path, 'wb') as fifo:
    fifo.write(chunk)  # 边读边写
```

失败时回退到直接 `aplay <wav>`。

### 7. 跳过 sox 重采样，直接 44100Hz 播放（2026-05-02）

- 删除 `tts_synthesize()` 中调用 `sox` 将 44100Hz→16000Hz 的重采样步骤
- MeloTTS 输出原生 44100Hz FLOAT_LE WAV，直接由 aplay 播放
- `play_audio()` 已支持自动检测采样率并选择 `FLOAT_LE` / `S16_LE`

### 8. TTS 预热 socket 保持连接复用（2026-05-02）

- `tts_warmup()` 预热后**不关闭** socket，存入全局 `_tts_warmup_sock`
- `tts_synthesize()` 首次调用时优先使用预热 socket（省去一次 connect）
- 取走后恢复为每次新建 socket 的原有行为

## 2026-05-07：Streaming 服务重构 + 多轮对话 + Fast-boot 改造

### 背景

将 LLM 服务从 `qwen3_llm_service.py`（旧版，每次请求独立加载上下文）迁移到 `qwen3_llm_streaming_service.py`（新版，`keep_history=1` 预填充 + Unix Socket 流式通信）。同时将 TTS 改为常驻服务（`melotts_service_rknn.py`），主循环改为多轮对话模式（`streaming_vad.py`）。

### 改动的文件

| 文件 | 位置 | 说明 |
|------|------|------|
| `qwen3_llm_streaming_service.py` | `/userdata/voice_assistant/` | 新增 `PrefilledRKLLM` 类，`keep_history=1`，系统提示词预填充，`__RESET__` 命令重置上下文 |
| `melotts_service_rknn.py` | `/data/voice_assistant/` | 新增常驻 TTS 服务，带 `warmup`/`cancel_warmup` 机制 |
| `streaming_vad.py` | `/userdata/voice_assistant/` | 多轮对话 `while True` 循环，15 分钟超时自动 `llm_reset()`，LLM 线程启动即触发 `tts_warmup_async()` |
| `fast-boot-service.sh` | `/usr/local/bin/` | 替换旧版 boot 脚本：去掉 RAG，只启动 LLM + TTS + streaming_vad 主循环 |
| `run.sh` | `/data/voice_assistant/` | 增加 `start_service()` 函数，自动检测并启动 LLM/TTS 服务，等待 socket 就绪 |

### 架构变化

```
旧版：
  fast-boot-service.sh
    ├── RAG (rag_optimized_server.py)
    ├── LLM (qwen3_llm_service.py, 非流式)
    └── [按需] 客户端单独启动 TTS + streaming_vad

新版：
  fast-boot-service.sh
    ├── 1. LLM (qwen3_llm_streaming_service.py, keep_history=1, NPU cores 1+2)
    ├── 2. MeloTTS (melotts_service_rknn.py, NPU core 0)
    ├── 3. 等待 socket 就绪
    └── 4. streaming_vad.py (多轮对话主循环)
                  │
                  ├── ASR (NPU cores 0-2, 全核)
                  ├── LLM 线程 → 同时触发 TTS warmup
                  └── TTS synthesize → TTS 自动 cancel_warmup
```

### NPU 核心分配

| 服务 | RKNN_CORE_MASK | NPU 核心 | 说明 |
|------|---------------|----------|------|
| LLM | `6` (二进制 110) | Core 1 + 2 | 用户要求保留 Core 0 给 TTS |
| TTS | `1` (二进制 001) | Core 0 | `melotts_service_rknn.py` 子进程环境变量 |
| ASR | `7` (二进制 111) | Core 0 + 1 + 2 | 全核加速，仅持续几百 ms |

### 已知问题：rkllm 版本不匹配

**错误信息**：
```
I rkllm: rkllm-runtime version: 1.2.2
I rkllm: rkllm-toolkit version: 1.2.3
E rkllm: The rkllm-runtime version is lower than the rkllm-toolkit version.
         Please update rkllm-runtime to 1.2.3 or higher.
[Qwen3-LLM] ❌ 模型加载失败: rkllm_init 失败: -1
```

**根因**：Qwen3-0.6B 模型是使用 rkllm-toolkit 1.2.3 编译的（`rkllm-toolkit version: 1.2.3`），但开发板上的推理运行时 `librkllmrt.so` 版本为 1.2.2（`rkllm-runtime version: 1.2.2`）。运行时版本低于 toolkit 版本时，`rkllm_init()` 拒绝加载模型。

**影响**：`qwen3_llm_streaming_service.py` 启动失败 → `run.sh` 等待 socket 超时卡死。

**解决方案**：将 `/data/qwen3/librkllmrt.so` 升级到 1.2.3+。有两种途径：

1. **从官方 SDK 获取**（推荐）：在 RKNPU SDK 中找到 rkllm-runtime 1.2.3 的 `.so` 文件
   ```bash
   # 查找 SDK 中的 so
   find /path/to/rknpu2 -name "librkllmrt.so*"
   # 替换开发板上的版本
   scp librkllmrt.so root@192.168.138.136:/data/qwen3/librkllmrt.so
   ```

2. **从 RK3588 构建环境获取**：在构建 VM 上检查是否有安装
   ```bash
   # 查看现有版本
   /data/qwen3/librkllmrt.so --version 2>/dev/null || strings /data/qwen3/librkllmrt.so | grep version
   # 搜索系统内其他 rkllm so
   find / -name "librkllmrt.so*" 2>/dev/null
   ```

### 多轮对话流程

```
while True:
    1. 等待语音（Silero VAD + webrtc Voice Activity）
    2. ASR 识别（sherpa-onnx + Zipformer）
    3. LLM 线程启动 → 同时 tts_warmup_async() 触发 TTS 模型预热
    4. LLM 流式生成 → 逗号/句号分句 → 立即送 TTS 合成
    5. TTS 合成到达 → cancel_warmup() 停止预热 → 执行 synthesize
    6. aplay 播放 WAV → FIFO 流式播放
    7. 14s 无语音 → 回到步骤 1（保持 LLM 上下文）
    8. 15 分钟无语音 → llm_reset() 重置上下文 → 回到步骤 1
```

### 关键时序优化

1. **keep_history=1 预填充**：系统提示词在服务启动时加载到 NPU KV cache，每次推理省 ~15 tokens prefill 时间
2. **LLM 线程启动即预热 TTS**：`threading.Thread(target=tts_warmup_async).start()` 在 `llm_generate_streaming()` 之前触发，TTS 模型加载与 LLM 首 token 推理并行
3. **多轮不重置**：对话轮次间保持 KV cache，省去重复 prefill 系统提示词的时间
4. **15 分钟超时重置**：`llm_reset()` 发送 `__RESET__` 命令到 LLM 服务，异步销毁→重新初始化→预填充

## 后续可能的优化方向

1. **TTS 速度 0.7 → 0.8**：质量可接受前提下，预计再省 ~300ms
2. **减少 LLM max_tokens：60 → 40**：缩短 LLM 总生成时间
3. **VAD 参数微调**：1.5s 实际静音 vs 0.5s 阈值之间的排查
4. **TTS 全 keepalive 连接**：每次合成复用同一个 socket 连接，而非仅首次
5. **rkllm-runtime 升级到 1.2.3**：解决版本不匹配，解锁 keep_history=1 流式服务（阻塞项）
