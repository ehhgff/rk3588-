## 1. SenseVoice SER 集成背景

### 需求

在语音问诊系统中加入情感识别（SER），使 LLM 能感知患者情绪（中性/开心/悲伤/生气等），从而调整回答语气。

### 方案选择

| 方案 | 描述 | 状态 |
|------|------|------|
| **方案 A** | SenseVoice 替换 sherpa-onnx ASR，同时输出 ASR + SER | 放弃 |
| **方案 B（选定）** | sherpa-onnx 保持 ASR，SenseVoice 作为额外 SER 模块 | **采用** |

**方案 B 架构**：

```
音频输入
  ├→ sherpa-onnx-alsa → ASR 流式识别
  └→ arecord → WAV 文件 → SenseVoice RKNN → 情感标签
```

### 模型选择

使用阿里达摩院 SenseVoiceSmall 模型，支持多语言语音识别 + 情感识别。情感标签映射：

| ID | 英文 | 中文 |
|----|------|------|
| 0 | neutral | 中性 |
| 1 | happy | 开心 |
| 2 | sad | 悲伤 |
| 3 | angry | 生气 |
| 4 | fearful | 恐惧 |
| 5 | disgusted | 厌恶 |
| 6 | surprised | 惊讶 |
| 7 | other | 其他 |

## 2. ONNX 模型导出

### 导出脚本演变

SenseVoice 模型结构复杂（包含 encoder、decoder、CTC 等组件），需要剥离出 encoder + CTC 部分单独导出 ONNX。

共迭代 **6 个版本**的导出脚本：

| 脚本 | 说明 |
|------|------|
| `sensevoice_export_onnx.py` | 初版，动态输入尺寸 |
| `sensevoice_export_onnx_v2.py` | 调整输入输出结构 |
| `sensevoice_export_onnx_v3.py` | 进一步优化导出逻辑 |
| `sensevoice_export_onnx_fixed.py` | **关键修复**：固定输入尺寸（兼容 RKNN） |
| `sensevoice_export_simple.py` | 简化版导出 |
| `sensevoice_export_lstm.py` | LSTM 变体尝试（未采用） |

### 遇到的问题

**问题 1：动态输入尺寸导致 RKNN 转换失败**

RKNN-Toolkit2 要求 ONNX 模型输入尺寸固定，动态 batch/seq_len 会导致转换错误。

**解决**：在 `sensevoice_export_onnx_fixed.py` 中固定 `batch_size=1, seq_len=500`：

```python
def export_sensevoice_onnx_fixed(
    output_path="sensevoice_encoder_ctc_fixed.onnx",
    opset_version=14,
    batch_size=1,
    seq_len=500,
):
```

**问题 2：ONNX opset 版本兼容性**

高版本 opset 在 RKNN-Toolkit2 中不支持。

**解决**：使用 `opset_version=14`。

**问题 3：模型加载依赖 funasr 框架**

导出环境需要安装 funasr 和 modelscope，依赖较多。

**解决**：在 PC 端创建独立 conda 环境：

```bash
conda create -n sensevoice-rknn python=3.10
pip install torch==2.1.2 torchvision==0.16.2 --index-url https://download.pytorch.org/whl/cpu
pip install funasr modelscope onnx==1.14.0
```

### 最终 ONNX 模型

| 文件 | 大小 | 说明 |
|------|------|------|
| `sensevoice_encoder_ctc_fixed.onnx` | 1.2GB | 固定输入尺寸，opset 14 |
| `sensevoice_encoder_ctc.onnx` | 1.2GB | 动态输入尺寸（仅用于参考） |

## 3. RKNN 模型转换

### 转换脚本演变

共迭代 **6 个版本**的 RKNN 转换脚本：

| 脚本 | 说明 |
|------|------|
| `sensevoice_onnx_to_rknn.py` | 初版 |
| `sensevoice_onnx_to_rknn_v2.py` | 调整量化参数 |
| `sensevoice_onnx_to_rknn_v3.py` | 优化转换配置 |
| `sensevoice_onnx_to_rknn_v4.py` | 进一步调参 |
| `sensevoice_onnx_to_rknn_v5.py` | 尝试 INT8 量化 |
| `sensevoice_onnx_to_rknn_v6.py` | **最终版**：不设置 mean_values |

### 遇到的问题

**问题 1：mean_values / std_values 导致推理结果异常**

RKNN 默认会对输入做归一化（`mean_values=[[0,0,0]], std_values=[[1,1,1]]`），但 SenseVoice 的 Mel 频谱特征已经是 log 域数值，不需要额外归一化。设置归一化后推理结果完全错误。

**解决**：在 `sensevoice_onnx_to_rknn_v6.py` 中不设置 mean_values：

```python
config_kwargs = {
    "target_platform": target_platform,
    "optimization_level": 3,
}
# 不设置 mean_values / std_values
```

**问题 2：INT8 量化精度损失**

INT8 量化后模型从 1.2GB 降到 245MB，但情感识别准确率下降。

**解决**：同时保留 INT8（`sensevoice_encoder_ctc_int8.rknn`，245MB）和 FP16（`sensevoice_encoder_ctc_fp16.rknn`，471MB）版本，开发板使用 FP16 版本。

**问题 3：100 帧输入限制**

原始 ONNX 支持 500 帧输入，但 RKNN 转换后推理速度随帧数线性增长。500 帧推理耗时 > 2s，无法满足实时性。

**解决**：重新导出 ONNX 时限制 `seq_len=100`，生成 `sensevoice_encoder_ctc_100f_fp16.rknn`（460MB），推理耗时降至 ~450ms。

### 最终 RKNN 模型

| 文件 | 大小 | 帧数 | 精度 | 推理耗时 |
|------|------|------|------|----------|
| `sensevoice_encoder_ctc_100f_fp16.rknn` | 460MB | 100 | FP16 | ~450ms |
| `sensevoice_encoder_ctc_fp16.rknn` | 471MB | 500 | FP16 | ~2s+ |
| `sensevoice_encoder_ctc_int8.rknn` | 245MB | 500 | INT8 | ~1s+ |

开发板使用 **`sensevoice_encoder_ctc_100f_fp16.rknn`**（100 帧 FP16 版本）。

## 4. 服务端/客户端架构

### 设计思路

采用 **Unix Socket 常驻服务**模式，避免每次 SER 推理都重新加载模型（模型加载需 ~5s）。

```
streaming_vad.py
  → sensevoice_ser_client.py (socket 客户端)
    → /tmp/sensevoice_server.sock
      → sensevoice_server.py (socket 服务端)
        → RKNN 推理（NPU 加速）
```

### sensevoice_server.py

**位置**：`/data/sensevoice/sensevoice_server.py`

**功能**：常驻 Unix Socket 服务，加载 RKNN 模型后循环接收推理请求。

**协议**：

| 模式 | 请求格式 | 响应格式 |
|------|----------|----------|
| JSON 模式 | `{"mode":"ser","features":[[...]]}\n` | `{"emotion":"neutral","emotion_id":0,...}\n` |
| 二进制模式 | `8字节长度 + float32 特征数据` | `8字节长度 + JSON 响应` |

**情感标签映射**（CTC token → 情感）：

```python
EMO_MAP = {
    1: "neutral", 2: "happy", 3: "sad", 4: "angry",
    5: "fearful", 6: "disgusted", 7: "surprised",
}
```

**推理流程**：

1. 接收特征矩阵（shape: `[1, n_frames, 560]`）
2. 填充/截断到 `MAX_FRAMES=100`
3. `rknn.inference()` → CTC logits
4. argmax 解码 → 去重 → 去 blank → 提取情感标签
5. 返回 JSON 结果

**遇到的问题**：

**问题 1：ModuleNotFoundError: No module named 'sensevoice_ser_client'**

`streaming_vad.py` 中 import `sensevoice_ser_client` 时找不到模块。

**解决**：在 `streaming_vad.py` 开头添加：

```python
sys.path.insert(0, "/data/sensevoice")
```

**问题 2：SyntaxError: unterminated string literal**

在 prompt 中注入情感文本时，使用 f-string 包含换行符导致语法错误。

**解决**：改用 `chr(10)` 代替换行符：

```python
prompt = _ser_emotion_text + chr(10) + prompt
```

### sensevoice_ser_client.py

**位置**：`/data/sensevoice/sensevoice_ser_client.py`

**功能**：封装 SER 推理的 socket 通信逻辑，提供简洁的 API。

**核心 API**：

| 函数 | 说明 |
|------|------|
| `ser_from_wav(wav_path, max_frames=100)` | 从 WAV 文件提取特征 → 推理 |
| `ser_from_audio(audio, max_frames=100)` | 从 numpy 音频数组提取特征 → 推理 |
| `ser_from_feats(feats)` | 直接传入特征矩阵 → 推理 |
| `format_emotion(result)` | 格式化情感结果为可读字符串 |

### streaming_vad.py 中的 SER 集成

**配置常量**：

```python
SER_SERVICE_SOCK = "/tmp/sensevoice_server.sock"  # SenseVoice SER（情感识别）
```

**`ser_recognize_emotion()` 函数** — 调用 SER 服务进行情感识别：

```python
def ser_recognize_emotion(wav_path):
    """调用 SER 服务进行情感识别"""
    try:
        from sensevoice_ser_client import ser_from_wav
        result = ser_from_wav(wav_path)
        if result:
            emotion = result.get('emotion', 'neutral')
            emotion_id = result.get('emotion_id', 0)
            confidence = result.get('confidence', 0.0)
            return emotion, emotion_id, confidence
    except Exception as e:
        log_warn(f"SER 识别异常: {e}")
    return 'neutral', 0, 0.0
```

**`format_emotion_prompt()` 函数** — 将情感标签格式化为 LLM prompt 注入文本：

```python
def format_emotion_prompt(emotion):
    """将情感标签格式化为 prompt 注入文本"""
    prompts = {
        'neutral': '患者情绪：中性',
        'happy': '患者情绪：开心',
        'sad': '患者情绪：悲伤',
        'angry': '患者情绪：生气',
        'fearful': '患者情绪：恐惧',
        'disgusted': '患者情绪：厌恶',
        'surprised': '患者情绪：惊讶',
    }
    return prompts.get(emotion, '患者情绪：中性')
```

**主循环 SER 集成** — 在 RAG 检索前进行情感识别，将情感信息注入 LLM prompt：

```python
# 情感识别（SER）
emotion, emotion_id, confidence = ser_recognize_emotion(recording_path)
_ser_emotion_text = format_emotion_prompt(emotion)
log_info(f"情感识别结果: {emotion} (confidence: {confidence:.2f})")

# 将情感信息注入 LLM prompt
prompt = f"{_ser_emotion_text}\n{base_prompt}"
```

**服务可用性检查** — 在调用 SER 前检查服务是否在线：

```python
def _ser_service_available():
    """检查 SER 服务是否可用"""
    try:
        if not os.path.exists(SER_SERVICE_SOCK):
            return False
        sock = socket.socket(socket.AF_UNIX, socket.SOCK_STREAM)
        sock.settimeout(1)
        sock.connect(SER_SERVICE_SOCK)
        sock.close()
        return True
    except:
        return False
```

**问题 1：ModuleNotFoundError: No module named 'sensevoice_ser_client'**

`streaming_vad.py` 中 import `sensevoice_ser_client` 时找不到模块。

**解决**：在 `streaming_vad.py` 开头添加：

```python

```

在 prompt 中注入情感文本时，使用 f-string 包含换行符导致语法错误。

**解决**：改用 `chr(10)` 代替换行符：

## 5. 特征提取模块

### sensevoice_feat_extract.py

**位置**：`/data/sensevoice/sensevoice_feat_extract.py`

**功能**：将原始音频转换为 SenseVoice 模型所需的 Mel 频谱 + LFR 特征。

**参数**：

| 参数 | 值 | 说明 |
|------|-----|------|
| `SAMPLE_RATE` | 16000 | 采样率 |
| `N_MELS` | 80 | Mel 滤波器组数 |
| `FRAME_LENGTH` | 25ms | 帧长 |
| `FRAME_SHIFT` | 10ms | 帧移 |
| `LFR_M` | 7 | LFR 拼接帧数 |
| `LFR_N` | 6 | LFR 帧移 |
| `N_FFT` | 512 | FFT 点数 |
| `F_MIN` | 0.0 | 最低频率 |
| `F_MAX` | 8000.0 | 最高频率 |

**特征维度**：`(n_frames, 560)` — 每帧 80 mel × 7 LFR = 560 维

**处理流程**：

```
WAV 音频 (16kHz)
  → 分帧加窗 (Hamming, 25ms, 10ms 帧移)
  → STFT → Power Spectrum
  → Mel 滤波器组 (80 频带)
  → log(Mel)
  → LFR (拼接 7 帧，步长 6)
  → 填充/截断到 max_frames
  → (n_frames, 560) float32
```

**遇到的问题**：

**问题 1：scipy.signal.get_window 在 RK3588 上不可用**

开发板 Python 环境缺少 scipy。

**解决**：在开发板上安装 scipy：

```bash
pip install scipy
```

**问题 2：特征提取耗时较长**

纯 Python 实现的 Mel 频谱提取在 RK3588 CPU 上耗时 ~200ms。

**解决**：限制 `max_frames=100`（对应 ~1s 音频），将特征提取时间控制在 ~100ms 内。

## 7. SER 时序优化：300ms 静音触发提前推理

### 问题

SER 在 ASR 完成后串行执行，每次对话额外增加 ~460ms 延迟：

```
说话结束 → 800ms 尾部静音 → ASR 完成 → 460ms SER → prompt 构建
                                            ↑ 用户多等 460ms
```

### 方案

利用 ASR 尾部静音等待时间（800ms），在检测到 300ms 静音时提前触发 SER 推理，使 SER 与剩余 500ms 尾部静音并行执行：

```
说话结束 → 300ms 静音 → 触发 SER（~450ms）──┐
              └→ 500ms 剩余尾部静音 → ASR 完成 ──→ prompt 构建（SER 已就绪）
                                                    ↑ 零额外等待
```

### 实现细节

**`record_on_voice_detection(ser_ctx=None)`** — 新增 `ser_ctx` 参数，接收 SER 上下文（wav 路径、arecord 进程）。

**ASR 等待循环中新增 300ms 静音检测**：

```python
# SER: 300ms silence trigger early inference
# 条件：有文本内容（大于4字）+ 300ms 静音
if ser_ctx and not _ser_triggered[0] and _last_data_time[0] > 0 and len(_all_texts[0]) > 4:
    if time.time() - _last_data_time[0] >= 0.3:
        _ser_triggered[0] = True
        _do_ser_early(ser_ctx)
```

**SER 触发条件演进**：

| 版本 | 触发条件 | 问题 |
|------|----------|------|
| 初版 | 有文本内容（至少2字）+ 300ms 静音 | 未说话时误触发，短文本（如"你好"）也触发 |
| **最终版** | **文本大于4字 + 300ms 静音** | 避免短文本和噪音误触发 |

**新增辅助函数**：

| 函数 | 作用 |
|------|------|
| `_do_ser_early(ctx)` | 停止 arecord → 调用 `ser_from_wav()` → 保存结果到 ctx |
| `_wait_ser_early(ctx)` | 等待提前推理完成（当前为空操作，推理在主循环完成） |
| `_get_ser_emotion_text(ctx)` | 从 ctx 提取情感标签，格式化为 prompt 注入文本 |

**主循环 SER 代码简化**：

```python
# 旧：ASR 完成后串行录音 → 推理
_ser_arecord_proc = subprocess.Popen(["arecord", ...])
recording_frames, streaming_text = record_on_voice_detection()
# 停止录音 → ser_from_wav() → 耗时 ~460ms

# 新：ASR 期间并行录音，尾部静音时提前推理
_ser_ctx = {"wav_path": ..., "arecord_proc": ..., "result": None}
recording_frames, streaming_text = record_on_voice_detection(_ser_ctx)
# 直接取结果，零额外延迟
_ser_emotion_text = _get_ser_emotion_text(_ser_ctx)
```

### 参数调整

`rule2-min-trailing-silence`: **1.0s → 0.8s**

使 ASR 尾部静音等待时间与 SER 推理时间（~450ms + 300ms 触发阈值 ≈ 750ms）对齐，确保两者几乎同时完成。

### 遇到的问题

**问题 1：SyntaxError: closing parenthesis ')' does not match opening parenthesis '{'**

使用 `sed` 替换 `streaming_vad.py` 中的 Popen 调用时，破坏了 Python 语法结构，导致 `subprocess.Popen(` 后的参数丢失。

**解决**：创建 `fix_popen.py` 修复脚本，恢复正确的 Popen 调用格式：

```python
proc = subprocess.Popen(
    cmd, stdout=subprocess.DEVNULL, stderr=slave_fd,
    env={**os.environ,
         'LD_LIBRARY_PATH': f"{SHERPA_ONNX_LIB}:{os.environ.get('LD_LIBRARY_PATH', '')}"}
)
```

## 8. 其他系统优化

### 音量设置调整

**修改前**：音量设置为 200%（`amixer set Master 200%`）

**修改后**：音量设置为 40%（`amixer set Master 40%`）

200% 音量导致音频失真（削波），降低到 40% 后音质清晰，适合近距离对话场景。

```python
def setup_audio():
    """初始化音频设备"""
    subprocess.run(["amixer", "set", "Master", "40%"], capture_output=True)
```

### RAG 直接回答延迟移除

**问题**：RAG 命中后等待 0.5s 再播放，增加不必要的响应延迟。

**修改前**：

```python
if patient_rag_answer:
```

## 9. ASR 引擎替换：Zipformer → Paraformer

### 背景

原 Zipformer 流式模型（`encoder-epoch-99-avg-1.rknn`）识别准确率不够理想。sherpa-onnx 1.13.0 原生支持流式 Paraformer，中文识别准确率通常优于 Zipformer。

### 模型选择

从 ModelScope 的 `speech_paraformer_asr_nat-zh-cn-16k-common-vocab8404-online` 转换的 sherpa-onnx 格式模型：

| 文件 | 大小 | 说明 |
|------|------|------|
| `encoder.onnx` | 607MB | FP32 编码器 |
| `encoder.int8.onnx` | 158MB | INT8 量化编码器 |
| `decoder.onnx` | 218MB | FP32 解码器 |
| `decoder.int8.onnx` | 69MB | INT8 量化解码器 |
| `tokens.txt` | 74KB | 词表（8404 词） |

### 架构差异

| 项目 | Zipformer（旧） | Paraformer（新） |
|------|----------------|-----------------|
| 模型格式 | RKNN（NPU） | ONNX（CPU） |
| 推理后端 | NPU (`--provider=rknn`) | CPU (`--num-threads=4`) |
| 命令行参数 | `--encoder` / `--decoder` / `--joiner` | `--paraformer-encoder` / `--paraformer-decoder` |
| 环境变量 | `RKNN_CORE_MASK=6` | 不需要 |

### 代码改动

**配置常量替换**：

```python
# 旧

ZIPFORMER_DIR = "/data/zipformer"
ENCODER_MODEL = f"{ZIPFORMER_DIR}/model/encoder-epoch-99-avg-1.rknn"
DECODER_MODEL = f"{ZIPFORMER_DIR}/model/decoder-epoch-99-avg-1.rknn"
JOINER_MODEL = f"{ZIPFORMER_DIR}/model/joiner-epoch-99-avg-1.rknn"
TOKENS_PATH = f"{ZIPFORMER_DIR}/model/vocab.txt"

# 新
PARAFORMER_STREAMING = True
PARAFORMER_DIR = "/data/paraformer"
PARAFORMER_ENCODER = f"{PARAFORMER_DIR}/encoder_fp32.onnx"
PARAFORMER_DECODER = f"{PARAFORMER_DIR}/decoder_fp32.onnx"
TOKENS_PATH = f"{PARAFORMER_DIR}/tokens.txt"
```

**两处 sherpa-onnx-alsa 调用修改**：

1. `_warmup_asr()` — 预热函数
2. `record_on_voice_detection()` — 主识别函数

均将 `--encoder` / `--decoder` / `--joiner` + `--provider=rknn` 替换为 `--paraformer-encoder` / `--paraformer-decoder` + `--num-threads=4`。

## 12. Matcha-TTS 模型常驻内存优化（2026-05-16）

### 问题

Matcha-TTS 使用 `sherpa-onnx-offline-tts` 命令行工具合成语音，每次调用都重新加载模型：

| 阶段 | 耗时 |
|------|------|
| 模型加载（声学模型 + 声码器） | ~3.5s |
| 纯推理（声学模型 + 声码器） | ~0.7s |
| **总耗时** | **~4.2s** |

核心问题：`sherpa-onnx-offline-tts` 是 C++ 独立进程，进程间内存隔离，预热无法缓存模型。

### 解决方案

使用 **ONNX Runtime Python API** 直接加载模型，通过常驻 Unix Socket 服务保持模型在内存中。

**架构变更**：

```
旧: streaming_vad.py → subprocess(sherpa-onnx-offline-tts) → 每次加载模型 (~4.2s)
新: streaming_vad.py → Unix Socket → matcha_tts_service.py (ONNX Runtime, 模型常驻) → 仅推理 (~0.3s)
```

### 实现细节

#### matcha_tts_service.py

**位置**：`/data/voiceassistant/core/matcha_tts_service.py`

**核心类**：

| 类 | 职责 |
|------|------|
| `MatchaTTSInference` | 加载模型 + G2P + 推理（声学模型 + 声码器 + ISTFT） |
| `MatchaTTSService` | Unix Socket 常驻服务，接收合成请求 |

**模型加载（启动时一次性加载）**：

```python
# 声学模型：model-steps-3.onnx
# 输入: x(int64[N,L]), x_length(int64[N]), noise_scale(float32[1]), length_scale(float32[1])
# 输出: mel(float32[N,80,L])
self.am_session = ort.InferenceSession(ACOUSTIC_MODEL, sess_options=session_opts)

# 声码器：matcha_vocoder.onnx
# 输入: mels(float32[1,80,time])
# 输出: mag(float32), x(float32), y(float32) → 复数频谱 = mag * (x + j*y)
self.vocoder_session = ort.InferenceSession(VOCODER_MODEL, sess_options=session_opts)
```

**推理流水线**：

```
文本 → G2P (lexicon.txt + tokens.txt) → token IDs (int64)
  → 声学模型推理 → mel 频谱 (float32[1,80,T])
    → 声码器推理 → mag, x, y (复数频谱)
      → ISTFT (scipy.signal.istft, n_fft=1024, hop_length=256, hann窗)
        → 音频波形 → WAV 文件 (22050Hz, 16-bit PCM)
```

**G2P 实现**：

```python
# 中文字符 → lexicon.txt 查表 → 拼音 token 序列
# 英文字母 → tokens.txt 查表 → 字母 token
# 标点符号 → tokens.txt 查表 → 标点 token
pattern = re.compile(r"[\u4e00-\u9fff]+|[a-zA-Z0-9]+|.")
```

**Socket 协议**：

| 命令 | 请求格式 | 响应格式 |
|------|----------|----------|
| `ping` | `{"command": "ping"}` | `{"status": "ok", "model_loaded": true}` |
| `synthesize` | `{"command": "synthesize", "text": "...", "output": "/path/to/output.wav"}` | `{"status": "ok", "output": "...", "time_ms": 327}` |

### 技术要点

1. **ONNX Runtime SessionOptions**：`intra_op_num_threads=2` 控制 CPU 线程数，避免过度抢占

3. **音频输出**：22050Hz 16-bit PCM 单声道 WAV，`scipy.signal.istft` + `wave` 模块写入
4. **进程管理**：PID 文件 `/tmp/matcha_tts.pid`，支持 SIGTERM/SIGINT 优雅退出
5. **Socket 权限**：`os.chmod(SOCKET_PATH, 0o777)` 确保多进程可访问
