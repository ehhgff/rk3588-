## 1. LLM：开启 enable_thinking=False 解决"不说人话"

### 问题

DeepSeek-R1-CMtMedQA 模型输出中包含思维链（thinking chain），导致回答像"内心独白"而非直接回答。用户描述："之前改动之后就不说人话了"。

### 根因

RKLLM 的 `enable_thinking` 参数默认为 `True`，使 DeepSeek-R1 输出推理过程。这些推理内容泄露到最终回答中，语气不像医生直接对患者说话。

### 解决

在 `qwen3_llm_streaming_service.py` 中将两处 `enable_thinking = True` 改为 `False`：

- 第 198 行：prefill/system prompt 阶段
- 第 243 行：用户输入推理阶段

### 结果

LLM 输出不再包含思维链，直接以医生口吻回答问题。

### 源文件

- `qwen3_llm_streaming_service.py` L198, L243

## 2. RAG：35岁 → 三十五岁解决年龄不匹配

### 问题

用户问"您是三十五岁吗"时 RAG 没有命中，因为 ASR 输出中文数字"三十五"，但 `patient_data.json` 中存的是阿拉伯数字"35"。

### 根因

Bigram Jaccard 相似度匹配对"三十五"和"35"视为完全不同的字符串，相似度为 0。

### 解决

将 `patient_data.json` 中所有"35"替换为"三十五"，包括：
- `age` 字段："35岁" → "三十五岁"
- 对话模板中的问句："您是35岁吗" → "您是三十五岁吗"
- 回答："是的，我今年35岁" → "是的，我今年三十五岁"

### 结果

"您是三十五岁吗" → RAG 命中 → 直接回答"是的，我今年三十五岁"（跳过 LLM，走直通路径）。

### 源文件

- `patient_data.json` — 所有 age 相关字段

## 3. RAG：始终注入上下文（不论是否离题）

### 问题

RAG 上下文只在 `is_off_topic=False` 且 `confidence >= 0.30` 时注入 prompt。离题查询完全没有患者档案参考。

### 根因

RAG 注入逻辑中，`rag_context` 只在 `topic and answer` 或 `answer and close_matches` 时才被赋值。离题时 topic 为 None、close_matches 可能为空，导致 `rag_context` 为 None。

### 解决

重写 RAG 注入逻辑：只要 RAG 返回了有效信息（topic+answer 或 close_matches+answer），就注入 prompt 作为上下文。不再检查 `is_off_topic`。

### 代码逻辑

```python
if topic and answer:
    rag_context = f"患者档案参考——{topic}：{answer}"
elif answer and rag_result.get("close_matches"):
    cm = rag_result["close_matches"][0]
    rag_context = f"患者档案参考——{cm.get('topic', '相关')}：{cm.get('answer', answer)}"
```

### 结果

无论查询是否离题，LLM 都能看到患者档案信息，辅助判断。

### 源文件

- `streaming_vad.py` — RAG 注入部分（~L944-961）

## 4. TTS：断句重写解决句间空白

### 问题

TTS 合成时，句与句之间存在明显空白停顿。用户描述："tts中间有空白，断句机制有问题"。

### 根因

原断句逻辑贪心切分，第一句太短（如"1.您好！感谢您的信息。根据您的描述，" → 只切到"1.您好！"就送去 TTS，剩余长句等待时间长）。

期望的分割点：
```
1.您好！感谢您的信息。根据您的描述，
2.如果您没有出现明显的症状...
5.并告知医生您的年龄和感冒情况。
```

### 解决

重写断句逻辑为三级优先级：

1. **优先**：`。！？` 结尾且长度 >= `MIN_FIRST`（首句 10 字）/ `MIN_NORMAL`（后续 5 字）
2. **降级**：超过 `MAX_CHARS=35` 字 → 找最后一个 `，、；` 切分
3. **硬切**：超过 `HARD_CUT=30/25` 字且无逗号 → 直接切

关键参数：
```python
MIN_FIRST = 10    # 首句最少字数
MIN_NORMAL = 5    # 后续句子最少字数
MAX_CHARS = 35    # 触发逗号回退的字数
HARD_CUT = 30     # 首句硬切上限
```

### 结果

TTS 合成节奏更均匀，句间空白消除。

### 源文件

- `streaming_vad.py` — `_llm_worker()` 中的 `_split_sentence()` 逻辑

## 5. TTS：MeloTTS 参数修复语调

### 问题

MeloTTS 语音语调奇怪，用户描述"语调很奇怪"。

### 根因

之前为了降延迟把 `noise_scale` 从默认 0.6 改成了 0.667，但偏离了 MeloTTS 原厂参数。MeloTTS 的原始默认值更适合中文语音合成。

### 解决

恢复 MeloTTS 默认参数：
```python
noise_scale: 0.6      # 从 0.667 改回
noise_scale_w: 0.8    # 新增（之前未设置）
sdp_ratio: 0.0        # 新增（之前未设置）
```

注：`noise_scale_w` 和 `sdp_ratio` 是 MeloTTS 的 VITS 解码器参数，控制音色变化和时长分布。

### 源文件

- `streaming_vad.py` — `tts_synthesize()` request 字典（~L749-751）

## 6. 离题处理：LLM 自行判断，不再依赖 RAG

### 问题

用户说"唱首歌吧"，LLM 回答"好的，请继续..."。用户反馈"矫正效果没有"。

### 最初尝试

用 RAG 返回的 `is_off_topic` 字段构建矫正 prompt：
```python
if is_off_topic and rag_context:
    prompt = f"""用户问了一个与看病无关的问题："{recognized_text}"
患者回应："{rag_context}"
请模拟一位医生，先幽默地回应一下这个离题的问题，再巧妙地把话题拉回到问诊上。
助手："""
```

### 推翻

用户指示："是否离题由llm判断" + "prompt里让他简短，但是注重医疗逻辑去询问或者推断"。

### 最终方案

去掉基于 RAG `is_off_topic` 的矫正逻辑。改为在 prompt 中加入角色指令，让 LLM 自行判断并处理：

```python
prompt = f"你是医生。回答简短，注重医疗逻辑。如果患者的问题和看病无关，先幽默回应，再把话题拉回问诊。\n用户：{recognized_text}\n（请只用中文回答，不要包含任何英文）\n助手："
```

### 预期效果

- "唱首歌吧" → LLM 自行判断为离题 → "哈哈，我这儿不是KTV。来，说说你哪里不舒服？"
- "我头痛" → RAG 上下文 + LLM 医疗推理 → 正常回答
- "请问您是三十五岁吗" → RAG 直通路径 → 直接回答（跳过 LLM）

### 源文件

- `streaming_vad.py` — prompt 构造（~L917）

## 8. TTS 引擎替换：MeloTTS → Matcha-TTS（2026-05-14）

### 背景

将 TTS 引擎从 MeloTTS (VITS, RKNN NPU, 子进程) 替换为 **Matcha-TTS (Flow Matching, ONNX CPU, 医疗词典增强)**。

### 改动的文件

| 文件 | 操作 | 说明 |
|------|------|------|
| `matcha_tts_service.py` | **新建** | Matcha-TTS socket 常驻服务，兼容原协议 |
| `streaming_vad.py` | **修改** | `TTS_SERVICE_SOCK` → `/tmp/matcha_tts.sock`；分句参数适配 RTF 0.3 |
| `fast-boot-service.sh` | **修改** | 替换 MeloTTS 启动逻辑；socket 清理路径 |
| `run.sh` | **修改** | `TTS_SCRIPT`/`TTS_SOCK`；TTS 启动逻辑 |
| `S98matchatts` | **新建** | 开机自启 init 脚本，替换 S98melotts |
| `optimize_matcha_onnx.py` | **新建** | ONNX FP16 量化 + 基准测试工具 |

### 性能对比

| 指标 | MeloTTS (旧) | Matcha-TTS (新) |
|------|-------------|-----------------|
| 每次合成耗时 | ~3.3s | **~1.92s** |
| RTF | 较高 | **0.27** |
| 医疗词典 | 无 | **572 词条** |
| 输出采样率 | 44100Hz | 22050Hz |
| 运行单元 | NPU (Core 0) | **CPU (ONNX)** |

### 新架构

```
streaming_vad.py
  → socket /tmp/matcha_tts.sock
    → matcha_tts_service.py
      → subprocess sherpa-onnx-offline-tts
        → model-steps-3.onnx + vocos-22khz-univ.onnx
          → lexicon.txt (66,939 词条，含 572 医疗词汇)
```

### NPU 核心重分配

Matcha-TTS 走 CPU 后，NPU Core 0 不再被 TTS 占用：

| 服务 | 之前 | 现在 | 原因 |
|------|------|------|------|
| LLM | Core 1+2 (mask=6) | **Core 0+1+2 (mask=7)** | 全核加速 |
| ASR | Core 1+2 (mask=6) | **Core 0+1+2 (mask=7)** | 全核加速 |
| TTS | Core 0 (mask=1) | **CPU (ONNX)** | 不再占用 NPU |

LLM + ASR 现在共用全部 3 个 NPU 核心。

### 分句逻辑适配 RTF 0.3

Matcha-TTS 的 RTF ≈ 0.3（合成 1s 音频仅需 0.3s），分句参数放宽：

| 参数 | 旧值 | 新值 | 说明 |
|------|------|------|------|
| 首句句号切 | ≥10 字 | **≥15 字** | 等 1.5s 听到更完整首句 |
| 后续句号切 | ≥5 字 | **≥8 字** | 减少碎片 |
| 长句保护 | ≥35 字切 | **≥45 字** | 自然句可更长 |
| 首句硬切 | ≥30 字 | **≥35 字** | 兜底更宽松 |
| 后续硬切 | ≥25 字 | **≥30 字** | 同上 |

### ASR 尾部静音调整

`rule2-min-trailing-silence`: **1.0s → 0.7s**

配合 PTY + 800ms 数据空闲超时，ASR 结束检测更灵敏。

### 后续优化

- **FP16 量化**：`optimize_matcha_onnx.py` 已将 Matcha-TTS ONNX 模型转为 FP16，预计 RTF 从 0.27 降至 ~0.18，合成时间 ~1.2s
- **常驻推理**：从 subprocess 改为 Python ONNX Runtime 直接推理，消除模型加载开销
