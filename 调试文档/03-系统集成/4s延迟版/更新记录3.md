## 二、各文件详细变更

### 2.1 melotts_rknn_persistent.py — RKNN 常驻推理模块（新建）

将编码器 + 解码器 RKNN 模型常驻 NPU 内存，每次合成无需 reload 模型。

**旧方案**（已废弃）：
```
每次合成:
  fork 子进程 → melotts_demo 加载模型 → 推理 → 退出（~4.3s）
```

**新方案**：
```
服务启动:
  MeloTTSInference.load() → 加载 encoder.rknn + decoder.rknn → 常驻内存

每次合成:
  MeloTTSInference.synthesize(text) → enc.inference() + dec.inference() → WAV（~1.7s）
```

**核心类**：

```python
class MeloTTSInference:
    def load(self)              # 加载 encoder + decoder RKNN 模型 + lexicon
    def g2p(self, text)         # 中文文本 → 音素 ID 列表（lexicon.txt 逐字查询）
    def synthesize(self, text, output_path, speed=0.7, ...)
    def get_audio(self, text, ...)  # 返回 numpy 数组
    def release(self)             # 释放 NPU 内存
```

**关键优化**：

| 方面 | 旧子进程 | 新常驻 |
|------|---------|--------|
| 每次合成耗时 | ~4.3s | **~1.7s**（2.5× 加速） |
| 模型加载 | 每次从头加载 | 仅启动时一次（~3.7s） |
| 稳定性 | 子进程常崩溃 | 常驻进程稳定运行 |
| 音量 | 未归一化（峰值 ~0.12） | **峰值提升到 0.85** |

**音量归一化**：
```python
# 峰值检测 + 增益
peak = np.max(np.abs(audio_trimmed))
if peak > 0.001 and peak < 0.85:
    gain = 0.85 / peak
    audio_trimmed = audio_trimmed * gain
```

**API 兼容**：`synthesize`, `get_audio`, `release` — 服务层无需改动协议。

### 2.3 streaming_vad.py — 音频设备检测 + 播放修复

#### 2.3.1 音频设备自动检测（新）

**旧问题**：`RECORD_DEVICE = "plughw:0,0"` 和 `PLAY_DEVICE = "plughw:1,0"` 硬编码。USB 麦换口或换设备后 card 编号变化 → ASR 启动失败。

**新方案**：按设备名子串匹配，自动扫描 `arecord -l` / `aplay -l`。

```python
def _scan_audio_devices(list_cmd):
    """返回 [(card, device, name), ...]"""

def _find_device(devices, name_patterns, default):
    """按 name 子串匹配，返回 plughw:X,Y"""

# USB 麦克风：支持 AB13X / UACDemo 等型号
RECORD_DEVICE_NAMES = ["AB13X", "UACDemo"]
# USB 音箱
PLAY_DEVICE_NAMES = ["USB2.0 Device"]
```

**效果**：麦插 card 0 或 card 3，换不同型号的 USB 麦克风，都能自动检测到。

#### 2.3.2 ASR 尾部静音调整

| 参数 | 旧值 | 新值 |
|------|------|------|
| `rule1-min-trailing-silence` | 1.0 | **1.5** |
| `rule2-min-trailing-silence` | 0.5 | **1.0** |

减少说话被打断的几率。

#### 2.3.3 播放乱码修复

**根因**：`play_audio()` 使用 FIFO 管道 + `aplay -r -f -c` 参数时，将 WAV 文件**头部 44 字节**也当作 PCM 音频数据送入播放 → 开头一段噪声。

**修复**：去掉 FIFO，让 aplay 直接播 WAV 文件 → aplay 自动解析 WAV 头中的采样率/位深/声道。

```python
# 旧（FIFO，WAV 头当音频播 → 乱码）
aplay_cmd = ["aplay", "-D", PLAY_DEVICE, "-r", rate, "-f", "S16_LE", "-c", "1", fifo_path]

# 新（直接播 WAV，aplay 自动解析头部）
aplay_cmd = ["aplay", "-D", PLAY_DEVICE, "-q", output_file]
```

#### 2.3.4 Stale 进程清理

**问题**：streaming_vad 每轮启动新 sherpa-onnx-alsa，但旧进程（孤儿子进程）没被杀 → 
```
arecord: main:875: audio open error: Device or resource busy
```

**修复**：启动前先 kill 旧进程：
```python
os.system('pkill -9 -f sherpa-onnx-alsa 2>/dev/null')
time.sleep(0.3)
```

#### 2.3.5 超时时间

`NO_INPUT_TIMEOUT` 保持 900s（15分钟）。用户指出这个值太长 → 等待用户反馈后修改。

### 2.4 fast-boot-service.sh — 移除 streaming_vad 开机自启

**原因**：streaming_vad 之前的进程管理问题（stale sherpa-onnx 孤儿子进程导致设备忙）尚未彻底解决。移除后用户手动启动，方便调试。

**删除**：
- 启动 `streaming_vad.py` 的 nohup 命令
- 关联的 PID 记录

保留 LLM + TTS 自动启动。

## 四、已知问题

### 4.1 15 分钟超时太长

`NO_INPUT_TIMEOUT = 900`（15 分钟）对于实际使用过长。用户反映"等待时是 15 分钟，不是 1.5s/1.0s"。ASR 尾部静音（1.5s/1.0s）控制的是单句话结束检测，而这个 900s 是 LLM 上下文重置超时。**待用户确认期望值**。

### 4.2 streaming_vad 仍需手动启动

已从开机启动中移除，需手动：
```bash
cd /userdata/voice_assistant && python3 streaming_vad.py
```

### 4.3 多张 USB 声卡混插时检测不确定性

如果同时插入多个 USB 麦克风，设备名匹配逻辑取第一个匹配项。可能需要更精确的匹配规则。

### 4.4 音频播放是同步的

`play_audio()` 改为 `subprocess.run()`（同步等待播放完毕）。TTS 合成第一句后不会立即播放第二句（需等第一句播完）。可以通过多线程改善，但当前响应时间已控制在 ~4s（说话结束到出声），基本可接受。
