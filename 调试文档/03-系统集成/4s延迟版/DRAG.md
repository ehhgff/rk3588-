# RK3588 端侧医疗大模型部署文档（DRAG 蒸馏方案）

## 1. 项目背景与目标

本项目旨在将大语言模型（LLM）部署到端侧设备 **RK3588（8GB 内存）** 上，构建一个完全本地化、低延迟、隐私保护的**中文医疗问答助手**。核心目标为：

- **推理速度**：≥10 tokens/s，流畅对话；
- **回答质量**：专业、无幻觉、具备主动追问能力；
- **隐私安全**：用户数据完全离线处理，不上传云端。

## 2. 部署方案总览

### 2.1 整体架构

最终采用 **"DRAG 蒸馏 + CMeKG 知识图谱 + Qwen 模型家族"** 路线，实现从大模型到小模型的知识迁移，并在 RK3588 上完成高性能推理。

本方案由四个核心阶段组成：

- **知识底座构建**：使用 CMeKG 工具链提取医学实体与关系，生成疾病-症状-药物等三元组知识图谱。
- **教师模型证据生成**：以 Qwen2.5-7B-Instruct 作为教师，基于知识图谱为每个医学问题生成多条事实陈述（证据），替代传统 RAG 中的向量检索。
- **DRAG 蒸馏训练**：将教师生成的证据经过排序与知识图谱增强后，与原始问题一起作为训练目标，蒸馏至学生模型 Qwen2.5-0.5B-Instruct 中。
- **模型转换与端侧部署**：在 x86 PC 上使用 RKLLM-Toolkit 将蒸馏后的模型转换为 w8a8 量化的 `.rkllm` 文件，推送至 RK3588，配合 Runtime 1.2.2 实现纯本地 NPU 推理。

**技术架构**：
- **知识底座**：CMeKG 中文医学知识图谱（结构化三元组，覆盖疾病、药物、症状等）；
- **教师模型**：Qwen2.5‑7B‑Instruct（7B 参数，用于生成高质量医疗证据）；
- **学生模型**：Qwen2.5‑0.5B‑Instruct（0.5B 参数，经过 DRAG 蒸馏）；
- **蒸馏框架**：DRAG（Distilling RAG）——教师生成证据 → 证据排序 → 知识图谱构建 → 学生模型蒸馏；
- **模型转换**：RKLLM‑Toolkit 1.2.3（w8a8 量化）生成 `.rkllm` 文件；
- **端侧推理**：RKLLM Runtime 1.2.3，NPU 加速；
- **语音交互**（可选）：Qwen3‑TTS（RK3588 专用版本） + Paroli/Piper 中文 TTS。

### 2.2 软硬件环境

- **开发板**：RK3588 (8GB RAM)，NPU 驱动版本 v0.9.8。
- **板端运行时**：RKLLM Runtime 1.2.3，rknn_server 版本 ≥2.2.0（配套 Runtime）。
- **PC 端转换工具**：RKLLM-Toolkit 1.2.3（尽管存在已知兼容性隐患，见问题 4），Python 3.11。
- **训练环境**：云 GPU 实例（如 AutoDL RTX 3090），CUDA 12.4，显存 ≥24GB。
- **依赖框架**：LLaMA-Factory（用于部分 SFT 实验）、DRAG 官方实现、CMeKG 工具链。

## 3. DRAG 蒸馏方法详解

### 3.1 传统蒸馏失败的原因

在项目初期，我们先使用 **DeepSeek‑R1‑Distill‑Qwen‑1.5B** 进行医疗指令微调（LoRA），效果专业但速度约 12–15 t/s。为提升速度，尝试使用 **传统知识蒸馏（Logits-based KD）**，将微调过的 1.5B 教师模型的输出概率分布直接迁移至 0.5B 学生模型。

结果出现两个严重问题：

- **生造词与逻辑混乱**：学生模型输出中出现大量无意义词语（如"聣感"、"颸骨肿胀"），医学推理完全断裂。
- **输出无限重复**：生成时容易陷入反复输出同一 token 的循环，无法自然结束。

根本原因在于，0.5B 模型容量极小，直接模仿教师模型的 logits 只能学到表面的词频分布，却无法真正理解医学概念之间的逻辑关系。教师模型的知识是隐含在参数中的，传统蒸馏没有提供足够的显式知识信号，导致学生模型"鹦鹉学舌"但不知所云。

### 3.2 DRAG 的核心思想

DRAG 全称为 **Distilling RAG**，它将检索增强生成（RAG）的流水线能力蒸馏到小模型中。与传统蒸馏不同，DRAG 不仅传递输出分布，更将教师模型"如何查找证据、如何排序知识、如何构建推理链路"的整个思维过程显式地教给学生。

DRAG 由四个顺序步骤组成：

- **证据生成**：对于每个输入问题，教师模型不直接给出答案，而是先生成多条简洁的事实陈述（证据）。这些证据来源于教师内部的医学知识，相当于为每个问题临时构建了一个小型知识库。
- **证据排序**：采用双层排序策略——先用轻量语义相似度模型（如 sentence-transformers）进行粗筛，再用交叉编码器（cross-encoder）进行精排，选出与问题最相关的 top-k 条证据。这一步保证了输入给学生的是高纯度信息，减少噪声干扰。
- **知识图谱构建**：从筛选后的证据中，使用 CMeKG 或通用实体关系抽取工具提取实体和关系，构建一个局部的结构化知识图谱。图谱将零散的证据组织成逻辑网络，帮助学生理解概念间的关联。
- **学生模型蒸馏**：将原始问题、排序后的证据、以及知识图谱整合成一个增强的 prompt，作为学生模型的训练目标。学生模型的学习目标不再是单纯模仿教师的 logits，而是学习如何基于这些显式证据进行推理和回答。训练过程中仍然使用语言建模损失，但输入包含了检索到的知识，从而将 RAG 流程内化到小模型中。

### 3.3 为什么 DRAG 能解决传统蒸馏的问题

**针对生造词与逻辑混乱**：DRAG 通过外部证据和知识图谱为学生模型提供了"知识锚点"。当学生模型被要求生成回答时，它已经看到了与问题相关的事实陈述和实体关系，因此输出受到这些显式知识的约束，从根本上抑制了幻觉和胡编乱造。即使在蒸馏后不接入外部检索，模型也学会了在参数内部模拟证据检索与推理的习惯。

**针对输出无限重复**：传统蒸馏模型陷入重复循环，部分原因是缺乏明确的生成终止信号，且模型在低容量下容易坍缩到高频 token。DRAG 在训练时引入了证据文本和结构化的图谱信息，增加了输入的多样性，避免了模型只记住几个高频 token。同时，经过 DRAG 训练的模型在生成时能更早识别出语义完整的停止点，配合适当的解码参数（如 repetition_penalty 和 eos_token_id 设置），即可自然结束。

## 4. 部署实施流程

### 4.1 知识图谱构建

使用 **CMeKG 工具链** 的医学实体识别和关系抽取功能，对医学文本进行分词、命名实体识别和关系抽取，构建包含疾病、症状、药物、检查等核心实体的三元组知识图谱。这些图谱作为教师模型生成证据时的背景知识库，也为证据排序和知识图谱构建步骤提供了领域词典。

### 4.2 教师模型证据生成

在云端 GPU 实例上部署 **Qwen2.5‑7B‑Instruct** 作为教师模型，利用 DRAG 设计的 Prompt 为 CMeKG 数据集中的每个医疗问题生成 15 条简洁事实陈述，形成证据集。生成的证据集与原始问答对一起，构成蒸馏训练的数据基础。

### 4.3 DRAG 蒸馏训练

将生成的证据进行双层排序并构建知识图谱后，与原始问题组成增强训练样本，对 **Qwen2.5-0.5B-Instruct** 进行全量微调。蒸馏超参数：温度 4.0，α=0.7，学习率 3e-5，3 epoch，采用 bf16 混合精度。训练完成后，学生模型不再需要教师模型或外部检索即可独立回答医疗问题。

### 4.4 模型转换与量化

在 x86 PC 上使用 RKLLM-Toolkit 加载蒸馏后的模型（HuggingFace 格式），并执行 **w8a8 量化**，输出 `.rkllm` 文件。转换过程中需注意清理配置文件中的列表类型字段（详细见问题 4）。

### 4.5 板端部署与验证

将生成的 `.rkllm` 文件与匹配版本的 `librkllmrt.so`、`rknn_server` 部署至 RK3588。使用 Python API 推理，速度达 **40+ tokens/s**，首 token 延迟 **<200ms**。验证推理速度与回答质量，并确认 NPU 负载正常。

## 5. 遇到的问题与解决方法

### 问题 1：云端训练实例无操作自动休眠

**现象**：长时间蒸馏训练时，云端 Notebook 因无交互被自动关闭，训练进度丢失。

**解决方法**：编写心跳脚本，每 5 分钟向 Jupyter 后端发送 HTTP 请求保持活跃。若发生中断，利用框架保存的 checkpoint 进行续训。

### 问题 2：HuggingFace 资源无法下载

**现象**：下载教师模型或数据集时出现网络不可达或超时。

**解决方法**：设置环境变量 `USE_MODELSCOPE_HUB=1` 强制从国内 ModelScope 源下载；或使用 `HF_ENDPOINT=https://hf-mirror.com` 镜像；亦可手动用 git 克隆模型到本地再指定路径。

### 问题 3：LoRA 微调训练卡在 0%

**现象**：LoRA 微调时训练进度卡在 0%，显存不足。

**解决方法**：开启混合精度 bf16 或 4-bit 量化加载，降低显存占用。

### 问题 4：传统知识蒸馏导致生造词和逻辑混乱

**现象**：0.5B 学生模型输出无意义词汇（如"聣感"），推理断裂。

**解决方法**：放弃传统 logits 蒸馏，改用 **DRAG 框架**。通过引入 CMeKG 知识图谱和教师生成的显式证据链，为学生模型提供结构化知识约束，从根本上消除幻觉，提升推理能力。

### 问题 5：RKLLM-Toolkit 加载模型时崩溃

**现象**：调用 `llm.load_huggingface()` 时抛出 `'list' object has no attribute 'keys'`。

**根本原因**：Toolkit 的内部 C 扩展在递归解析模型配置文件（尤其是 `generation_config.json`）时，没有对列表类型做判断，直接调用了字典专属的 `.keys()` 方法，当遇到如 `eos_token_id: [151645, 151643]` 这样的列表字段时触发崩溃。

**解决方法**：
- **临时修复**：手动编辑模型目录下的 `generation_config.json`，将 `eos_token_id` 从列表改为单个值（如 `151643`），或直接删除该字段。
- **自动化清理**：编写预处理脚本，递归遍历所有 JSON 配置，将值为标量列表的字段展开为第一个元素。
- **推荐方案**：降级到稳定的 **RKLLM-Toolkit 1.2.2** 进行转换，该版本无此缺陷，且与板端 Runtime 1.2.2 完全匹配。

### 问题 6：转换后 NPU 负载为 0%，纯 CPU 推理

**现象**：模型转换成功，但开发板上 NPU 负载始终为 0，推理耗时较长。

**解决方法**：板端的 `rknn_server` 版本（如 2.0.0b0）与 Runtime 1.2.2 不兼容。从 RKLLM SDK 中提取匹配的 `rknn_server` (aarch64) 和 `librkllmrt.so`，替换板端原有文件，并重启服务。之后 NPU 利用率恢复正常，推理速度达标。

### 问题 7：蒸馏模型输出无限重复单字或标点

**现象**：学生模型生成时开头或末尾出现大段重复字（如"您您您"或"的的的"）。

**解决方法**：
- 在推理时显式设置 `eos_token_id` 和 `pad_token_id`，并开启 `repetition_penalty=1.5`、`no_repeat_ngram_size=3`。
- 删除模型目录中可能残留的 `chat_template.jinja`，避免模板冲突。
- 必要时在生成参数中设置 `suppress_tokens` 抑制重复 token。

### 问题 8：数据集注册与格式不匹配导致训练中断

**现象**：训练启动时提示 `Undefined dataset cmtmedqa_multiturn in dataset_info.json`，或数据加载时出现 `KeyError: 'conversations'`。

**解决方法**：
- 检查 LLaMA-Factory 的 `dataset_info.json` 是否正确注册了自定义数据集，确保 `file_name` 字段指向实际存在的 JSON 文件，`formatting` 字段与实际数据结构一致（如 `sharegpt` 或 `alpaca`）。
- 使用 Python 快速查看数据集样本键名，根据实际字段（如 `instruction`/`output` 或 `conversations`）调整数据集配置或预处理脚本，保证训练脚本能正确解析。

### 问题 9：`TokenizersBackend does not exist`

**现象**：模型转换时报错，找不到 TokenizersBackend。

**解决方法**：降级 tokenizers 版本或新建干净 Conda 环境，严格安装依赖。

### 问题 10：语音合成模型转换失败

**现象**：MeloTTS 转换 ONNX 失败，依赖混乱。

**解决方法**：直接使用社区已转换的 Paroli 中文 RKNN 模型（huayan‑medium），避免自行转换的依赖冲突。

## 6. 最终效果

**DRAG 蒸馏后的 Qwen2.5‑0.5B 医疗模型**，在 RK3588 上经 w8a8 量化部署，达到以下指标：

- **推理速度**：40+ tokens/s
- **首 Token 延迟**：< 200 ms
- **回答质量**：能给出鉴别诊断，主动追问病史，输出专业、安全且无幻觉
- **隐私性**：全程离线运行，无需上传用户数据
- **可扩展性**：可进一步接入语音识别与合成模块，实现语音交互

典型输出示例：

> 患者：头痛发热3天  
> 助手：根据症状，可能是流行性感冒或上呼吸道感染。建议多饮水、监测体温（>38.5℃可服用退烧药），如持续加重或出现呼吸困难，请及时就医。请问有咳嗽、咳痰或全身酸痛吗？

## 7. 总结与展望

本项目成功在 RK3588 端侧部署了专业级中文医疗助手，解决了隐私、延迟、成本三角矛盾。DRAG 蒸馏被证明是兼顾速度与质量的有效路径。未来可进一步引入**检索增强生成（RAG）**，将 CMeKG 知识库作为动态证据源，持续提升回答的准确性和可溯源性；同时可探索剪枝‑蒸馏联合优化，进一步压缩模型体积。

本部署文档完整记录了端侧大模型从训练到落地的全过程，为同类场景提供了可复用的实践参考。
