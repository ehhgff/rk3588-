## 1. TTS 引擎替换：MeloTTS → Paroli（Piper TTS）

### 问题

原有 MeloTTS（Matcha-TTS）引擎存在以下问题：
- ONNX 模型在 CPU 上推理，速度慢
- Python 服务进程频繁重启，模型不能常驻内存
- 语调生硬，"像人机"
- 句子间停顿控制不灵活

### 方案选择

| 方案 | 描述 | 状态 |
|------|------|------|
| **方案 A** | 继续优化 MeloTTS 参数 | 放弃 |
| **方案 B（选定）** | **迁移到 Paroli（Piper TTS C++ 引擎）** | **采用** |

**选定方案 B 的原因**：
- Piper TTS 原生支持 C++ 推理，适合嵌入式
- 解码器可转换为 RKNN 格式，走 NPU 加速
- C++ 守护进程模式天然支持模型常驻内存

### 架构变更

```
旧架构：
MeloTTS（Python, ONNX CPU）→ 每次请求加载模型

新架构：
Paroli（C++, onnxruntime + RKNN NPU）→ 常驻 daemon，零加载开销
```

### 模型文件

| 文件 | 说明 |
|------|------|
| `encoder_streaming.onnx` | 编码器（ONNX，CPU 推理） |
| `decoder_streaming.rknn` | 解码器（RKNN，NPU 推理） |
| `zh_CN-huayan-medium.onnx.json` | 模型配置（音素、说话人、推理参数） |

### 源文件

- `/home/ubuntu/桌面/ai/paroli/piper/piper.cpp` — 推理主逻辑
- `/home/ubuntu/桌面/ai/paroli/piper/rknn-inferer.cpp` — RKNN 解码器推理封装
- `/home/ubuntu/桌面/ai/paroli/paroli-socket-server/main.cpp` — C++ Socket 守护进程

## 2. Paroli 模型常驻 C++ Socket 守护进程

### 设计

开发 C++ 守护进程 `paroli-socket-server`，通过 Unix Socket 提供 TTS 服务。

### 协议

| 方向 | 格式 | 说明 |
|------|------|------|
| 请求 | `{"text":"你好世界"}\n` | JSON，带换行终止 |
| 响应 | `{"status":"ok","size":12345,"path":"/tmp/..."}\n` | 返回 WAV 文件路径 |

### 预热机制

启动时自动执行一次空转合成（写入 `/dev/null`），确保首次请求不额外耗时：

```cpp
// main.cpp: 模型加载后立即预热
piper::textToWavFile(piperConfig, voice, "测试", nullOut, result);
```

预热耗时约 150ms，之后每次请求 TTS 合成耗时约 150-210ms。

### 启动命令

```bash
/data/paroli/bin/paroli-socket-server \
  --encoder /data/paroli/model/encoder_streaming.onnx \
  --decoder /data/paroli/model/decoder_streaming.rknn \
  -c /data/paroli/model/zh_CN-huayan-medium.onnx.json \
  --socket /tmp/paroli_tts.sock \
  --core-mask 1
```

### 管理脚本

`/data/voice_assistant/paroli_tts_service.py` — Python 封装，管理 C++ 守护进程生命周期。

### 源文件

- `/home/ubuntu/桌面/ai/paroli/paroli-socket-server/main.cpp`
- `/home/ubuntu/桌面/ai/voice_assistant/rk3588/paroli_tts_service.py`

## 3. Paroli 模型推理参数调优（解决拖音和生成慢）

### 问题

首次部署后 TTS 出现两个严重问题：
1. **拖音**：句尾字音拖长 4s+（如"华"字在"我叫李华"中）
2. **生成慢**：TTS 合成耗时 ~2500ms，与预期 RTF 不符

### 根因

模型配置文件 `zh_CN-huayan-medium.onnx.json` 中的推理参数 `noise_w` 过高（1.8），导致随机时长预测器输出异常的长音素时长。

### 参数变更

| 参数 | 修改前 | 修改后 | 作用 |
|------|--------|--------|------|
| `noise_w` | 1.8 | **0.5** | 时长预测器噪声，降低后音素时长更稳定 |
| `noise_scale` | 0.95 | **0.667** | 生成噪声，影响语音自然度 |
| `length_scale` | 0.9 | 0.9（不变） | 语速控制 |
| `sentence_silence` | 0.8 | **0.5** | 句子间停顿 |

### 效果对比

| 指标 | 修复前 | 修复后 |
|------|--------|--------|
| 合成音频时长（"我叫李华"） | ~313s（异常） | ~2.5s（正常） |
| TTS 合成耗时 | ~2551ms | ~149ms |
| 拖音现象 | 句尾拖长 4s+ | 无拖音 |
| RTF | ~1000 | ~0.06 |

### 源文件

- `/data/paroli/model/zh_CN-huayan-medium.onnx.json` — 模型推理参数配置

## 4. TTS 音频追加修复（多短语句子覆盖问题）

### 问题

生成"我叫李华，我是医生"等多短语文本时，音频仅有"嗯"一声（0.5s），内容不完整。

### 根因

`piper.cpp` 中非分块路径下，多个短语的音频数据使用 `=` 赋值而非追加（`insert`），后面的短语覆盖了前面的音频。

### 修复

在 `/home/ubuntu/桌面/ai/paroli/piper/piper.cpp` 中，将非分块路径下的音频写入方式从覆盖改为追加：

```cpp
// 修复前：audioBuffer = voice.decoder->infer(...)
// 修复后：auto chunk = voice.decoder->infer(...); audioBuffer.insert(...)
```

### 效果

多短语文本（如"我叫李华，我是医生"）可正常生成完整音频，包含所有短语内容。

### 源文件

- `/home/ubuntu/桌面/ai/paroli/piper/piper.cpp`

## 5. ASR 引擎恢复：Paraformer ONNX → Zipformer RKNN

### 问题

之前的更新将 ASR 引擎从 Zipformer RKNN（NPU）切换为 Paraformer ONNX（CPU），导致：
1. **CPU 推理速度慢**，第一句话经常识别不到
2. **ASR 预热无效**（预热进程被杀死后重新加载，Paraformer ONNX 加载慢）
3. 用户反馈"命令行 sherpa-onnx 可以识别到第一句话，run.sh 不能"

### 根因

`streaming_vad.py` 的 ASR 配置使用 Paraformer + ONNX（CPU）：

```python
PARAFORMER_ENCODER = "/data/paraformer/encoder_fp32.onnx"
PARAFORMER_DECODER = "/data/paraformer/decoder_fp32.onnx"
```

而命令行测试使用 Zipformer + RKNN（NPU），推理速度快，预热后 NPU 缓存有效。

### 修复

将 ASR 引擎恢复为 Zipformer RKNN（NPU）：

```python
# Zipformer RKNN 识别参数（NPU 加速）
ZIPFORMER_DIR = "/data/zipformer/model"
ZIPFORMER_ENCODER = "/data/zipformer/model/encoder-epoch-99-avg-1.rknn"
ZIPFORMER_DECODER = "/data/zipformer/model/decoder-epoch-99-avg-1.rknn"
ZIPFORMER_JOINER = "/data/zipformer/model/joiner-epoch-99-avg-1.rknn"
ZIPFORMER_TOKENS = "/data/zipformer/model/vocab.txt"
ZIPFORMER_PROVIDER = "rknn"
```

### Sherpa-onnx-alsa 启动命令

```bash
/data/sherpa-onnx/install/bin/sherpa-onnx-alsa \
  --tokens=/data/zipformer/model/vocab.txt \
  --encoder=/data/zipformer/model/encoder-epoch-99-avg-1.rknn \
  --decoder=/data/zipformer/model/decoder-epoch-99-avg-1.rknn \
  --joiner=/data/zipformer/model/joiner-epoch-99-avg-1.rknn \
  --provider=rknn \
  --num-threads=4 \
  --decoding-method=greedy_search \
  plughw:0,0
```

### 模型文件

| 文件 | 大小 | 说明 |
|------|------|------|
| `encoder-epoch-99-avg-1.rknn` | 142MB | Zipformer 编码器（RKNN，NPU） |
| `decoder-epoch-99-avg-1.rknn` | 8MB | Zipformer 解码器（RKNN，NPU） |
| `joiner-epoch-99-avg-1.rknn` | 6.5MB | Zipformer Joiner（RKNN，NPU） |
| `vocab.txt` | 56KB | 词表文件 |

### 源文件

- `/home/ubuntu/桌面/ai/voice_assistant/rk3588/streaming_vad.py`

## 7. Patient RAG 路径移除 0.5s 硬延迟

### 问题

Patient RAG 直通路径中，TTS 合成完成后硬编码 `time.sleep(0.5)`，导致用户从说话结束到听到声音额外增加 0.5s 延迟。

### 修复

移除 `streaming_vad.py` 中的 `time.sleep(0.5)`，TTS 合成完成后立即播放：

```python
# 修复前
TIMING['play_start'] = time.time()
time.sleep(0.5)
play_audio(rag_output)

# 修复后
TIMING['play_start'] = time.time()
play_audio(rag_output)
```

### 效果

Patient RAG 路径延迟：`说话结束 → 播放首句` 从 ~1600ms（含 0.5s sleep + 播放延时）降至直接播放。

### 源文件

- `/data/voice_assistant/streaming_vad.py`（Patient RAG 处理分支）

## 8. SER 残留 socket 检测修复

### 问题

run.sh 使用 `verify_socket` 检测 SenseVoice SER 服务状态，但该函数仅检查 socket 文件是否存在（`[ -S "$1" ]`）。当 SER 进程已死但 socket 文件残留时，误判为"服务已在运行"，导致 SER 实际不可用。

### 修复

将 `verify_socket` 替换为 `check_socket`（实际尝试连接），避免被残留 socket 文件误导：

```bash
# 修复前
if verify_socket "$sock"; then
    echo "  ✅ ${name} 服务已在运行"

# 修复后
if check_socket "$sock"; then
    echo "  ✅ ${name} 服务已在运行"
```

同一问题也存在于 Paroli TTS 的启动检测中，一并修复。

### 效果

run.sh 启动时准确检测各服务运行状态，检测到残留 socket 时自动清理并重新启动服务。

### 源文件

- `/data/voice_assistant/run.sh`

## 9. NPU 核心分配方案

### RK3588 NPU 核心

RK3588 有 3 个 NPU 核心，核心掩码：
- NPU_CORE_0 = 1（核心 0）
- NPU_CORE_1 = 2（核心 1）
- NPU_CORE_2 = 4（核心 2）

### 当前分配

| 服务 | 核心 | 掩码 | 绑定方式 |
|------|------|------|----------|
| Paroli TTS | NPU_CORE_0 | 1 | `--core-mask 1` |
| SenseVoice SER | NPU_CORE_0 | 1 | `core_mask=RKNNLite.NPU_CORE_0` |
| Qwen3 LLM | NPU_CORE_1+2 | 6 | `RKNN_CORE_MASK=6` |
| Zipformer ASR | Auto | - | `--provider=rknn` |

### 冲突分析

| 可能冲突的组合 | 是否同时运行 | 结论 |
|---------------|-------------|------|
| TTS ↔ SER | ❌ 不会（TTS 在 LLM 之后） | 无冲突，共享 core 0 |
| TTS ↔ LLM | ❌ 不会（串行执行） | 无冲突 |
| SER ↔ LLM | ❌ 不会（SER 在 ASR 阶段） | 无冲突 |
| ASR ↔ TTS | ❌ 不会（先识别后合成） | 无冲突 |

### 源文件

- `/data/sensevoice/sensevoice_server.py` — SER 核心绑定
- `/data/voice_assistant/paroli_tts_service.py` — TTS 核心传递
- `/data/voice_assistant/run.sh` — LLM 核心掩码环境变量
